## Plan 2.1: Fix risk stage for negative weights (short signals)

**Files to modify:**
- `vinu_strategy/engine/risk.py`
- `tests/test_risk.py`

**Approach:**
1. Split weight handling into long (positive) and short (negative) positions
2. Separately cap long positions at `max_weight` and short positions at `-max_weight` (or a separate `max_short_weight` param)
3. Reserve `cash_floor` for the net exposure: `sum(longs) + abs(sum(shorts)) <= 1 - cash_floor`
4. Scale both long and short weights proportionally if total exposure exceeds the limit
5. Add a `short` risk method to skip normalization for strategies that handle short exposure themselves

**Alternative simpler approach (if short is not yet needed):**
1. Add a config-level `allow_short: bool` flag
2. When `allow_short=false`, clip negative weights to 0 and redistribute the weight to other symbols
3. Warn when negative weights are discarded

**Tests to add:**
- `test_normalize_with_shorts` — verify correct handling of mixed long/short weights
- `test_normalize_shorts_exceed_cap` — verify scaling when short exposure exceeds limits
- `test_normalize_allow_short_false` — verify negative weights are zeroed out

## Plan 2.2: Fix expression evaluator case sensitivity

**Files to modify:**
- `vinu_strategy/service.py`
- `vinu_strategy/engine/expression.py`

**Approach:**
1. In `_extract_feature_values()`, normalize all indicator keys to lowercase (e.g., `SMA_9` → `sma_9`)
2. In `evaluate_expression()`, provide a fallback lookup: try the key as-is, then try lowercase, then try uppercase
3. Update the context dict to always use normalized keys

## Plan 2.3: Add YAML schema validation

**Files to modify:**
- `vinu_strategy/models/strategy.py`
- `vinu_strategy/engine/registry.py`
- `tests/test_registry.py`

**Approach:**
1. Define a known-keys whitelist for each YAML section (top-level, pipeline, selection, allocation, timing, risk)
2. In `StrategyConfig.from_dict()`, after parsing, log warnings for any unknown keys found
3. Validate that `features_required` entries match known patterns from the feature catalog (regex: `^[a-z_]+[0-9]*$` or preset names)
4. Validate pipeline stage method names against known method lists
5. All validation warnings should include the strategy name and YAML file path

## Plan 2.4: Improve Parquet append efficiency

**Files to modify:**
- `vinu_strategy/storage/weights.py`

**Approach:**
1. **Option A (recommended)**: Use per-day Parquet files instead of per-year. Each evaluation creates a new file `{strategy}/{year}-{month}-{day}.parquet`. Reading aggregates all files in the directory.
2. **Option B**: Use PyArrow's `pq.write_to_dataset()` with Hive-style partitioning (`year={year}/month={month}/day={day}`).
3. **Option C**: Switch to a time-series database (InfluxDB, QuestDB) for weight storage.

**Tests to add:**
- `test_weight_storage_append_large_dataset` — performance benchmark
- `test_weight_storage_read_partitioned` — verify reads across partitions

## Plan 2.5: Implement scheduler for auto-evaluation

**Files to modify:**
- `vinu_strategy/cli.py`
- `vinu_strategy/service.py`

**New optional dependency:** `apscheduler` or Python's `schedule` library

**Approach:**
1. Add a `vinu-strategy schedule` CLI command that starts a background scheduler
2. Read all registered strategies and their `schedule` field
3. For each strategy, schedule `evaluate()` at the configured frequency using APScheduler's cron trigger
4. Log all scheduled evaluations to the run history
5. Optionally expose the scheduler status via a new `GET /scheduler` API endpoint

## Plan 2.6: Add DELETE endpoints

**Files to modify:**
- `vinu_strategy/server/routes_read.py` (or new `routes_write.py`)
- `vinu_strategy/storage/weights.py`
- `vinu_strategy/storage/meta.py`

**Approach:**
1. Add `DELETE /weights/{strategy}` — delete all weight history for a strategy
2. Add `DELETE /weights/{strategy}/{symbol}` — delete weight history for a specific symbol
3. Add `DELETE /runs/{strategy}` — delete run history for a strategy
4. Add `DELETE /runs/{strategy}/{run_id}` — delete a specific run
5. Update storage layer with corresponding delete methods
