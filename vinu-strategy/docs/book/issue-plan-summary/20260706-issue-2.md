## Issue 2.1: Risk stage breaks on negative weights (short signals)

**File:** `vinu_strategy/engine/risk.py:19-27`

**Problem:** The `risk_normalize` function uses `min(w, max_w)` to cap individual weights. This works for positive weights but **passes negative weights through unchanged**. When short signals (negative weights from expression evaluator) are present:

- `min(-0.167, 0.25)` = `-0.167` (negative survives)
- `capped_total = sum(capped.values())` can be zero or negative
- `scale = (1 - 0.1) / capped_total` can divide by zero or produce negative scale
- All weights get corrupted

**Impact:** Strategies producing short signals (like RSI mean reversion with overbought detection) produce incorrect portfolio weights.

**Example:** RSI mean reversion with AAPL (RSI=25 → +0.167) and MSFT (RSI=75 → -0.167):
```python
capped = {"AAPL": 0.167, "MSFT": -0.167}
capped_total = 0.0  # sum = 0!
scale = 0.9 / 0.0  # ZeroDivisionError
```

## Issue 2.2: Expression evaluator is case-sensitive for feature names

**File:** `vinu_strategy/engine/expression.py`
**Related:** `vinu_strategy/service.py:139-153` (`_extract_feature_values`)

**Problem:** The vinu-features API supports case-insensitive indicator names (`SMA_9` = `sma_9` = `Sma_9`). However, `_extract_feature_values` stores keys as returned by the API (which may vary), and the expression evaluator does strict dict lookup. A strategy using `SMA_9` in its expression may fail if the API returns `sma_9`.

**Impact:** Strategies can fail intermittently depending on API response casing. Hard to debug.

## Issue 2.3: No YAML schema validation

**File:** `vinu_strategy/models/strategy.py`

**Problem:** YAML files are loaded with `yaml.safe_load()` and passed directly to `StrategyConfig.from_dict()`. There is no schema validation. A typo like `methood: all` instead of `method: all` silently defaults to the fallback, and the author gets no warning.

**Impact:** Strategy authors get no feedback on configuration errors. Silent fallbacks mask bugs.

---

## Issue 2.4: Parquet append is O(n) per write

**File:** `vinu_strategy/storage/weights.py:60-63`

**Problem:** Each `append_weights` call reads the entire year's Parquet file into memory, concatenates with new rows, and rewrites the whole file. For frequent evaluations (daily × 5 years = ~1825 appends), this becomes increasingly slow and memory-intensive.

**Impact:** Degraded performance over time. Large Parquet files (~1M+ rows) cause slow writes and high memory usage.

---

## Issue 2.5: `schedule` field is parsed but never used

**File:** `vinu_strategy/models/strategy.py`, all YAML files

**Problem:** Every strategy YAML has a `schedule: daily | weekly` field that is parsed into `StrategyConfig.schedule` but never referenced by any scheduler or cron system. Strategies must be evaluated manually or via external cron.

**Impact:** No automated rebalancing. Users must set up their own scheduling.

---

## Issue 2.6: No DELETE endpoints in Web UI / API

**Files:** `vinu_strategy/server/routes_read.py`, `vinu_strategy/storage/weights.py`, `vinu_strategy/storage/meta.py`

**Problem:** The API has `GET` and `POST` endpoints for strategies, weights, and runs, but no `DELETE` endpoints to prune old data. Users cannot clean up stale weight history or old run logs via the API.

**Impact:** Data accumulates indefinitely. No way to clean up test runs or old strategies.
