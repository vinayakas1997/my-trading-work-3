## GROUP 0 — The docs' picture of the live layer is incomplete

### 0.1 `TradePlanOrchestrator` (3,063 lines) is a second, larger execution path that the vision and how-implemented docs barely mention

- **Title:** Two independent live executors; the docs map only one of them.
- **Explanation:** `vision-trding-system.md` B1 and `how-system-implemented.md` §13-§14 describe Layer 6 as
  `LiveScheduler` + the live-decision poller. `entrypoint.sh` starts **six** workers in one container, one of which
  (`vinu-live trade-plan-worker`) runs `TradePlanOrchestrator`: the actual entry / invalidation / contingency
  authority for trade plans. It contains guards and actions the docs list as missing: consecutive-loss cooldown,
  turbulence pause, broker-outage pause, event blackout, spread gate, stale-signal and stale-data guards, CVaR gate,
  vol-target scaling, signal-conflict blocking, TWAP-sliced entries, partial-fill confirmation, `reduce_only`
  exits, REDUCE / ADD classification, thesis re-check (off by default), a dormant 4-signal OOD detector
  (incl. Mahalanobis turbulence), runtime correlation trimming, auto-correcting reconciliation, trailing stop, time stop.
- **Evidence:** `orchestrator.py:88-96` (cooldown), `:171` (turbulence), `:507-533` (OOD detector, default `off`),
  `:550-610` (`_ACTION_CLASS_MAP` with REDUCE/ADD/EXIT), `:1160-1205` (outage / conflict / stale guards),
  `:1421-1424` (backstop stop on every entry). Docs: v2 items C1, C2, B1 claimed these absent — see corrections
  appended to `01-inconsistencies-v2.md`.
- **Where found:** `vinu-live/entrypoint.sh`, `vinu-live/vinu_live/trade_plan/orchestrator.py`,
  `vinu-live/vinu_live/trade_plan/guards.py`.
- **Solution:** Add the orchestrator to the layer map and to `how-system-implemented.md` as its own section
  (workers, cadence, which guards, which store: `trade_plan_book.db`). Re-state every "missing" item in v2 as
  missing-for-which-path.
- **What it will achieve:** Gap lists stop reporting features that exist and start reporting the real asymmetry
  between the two paths (items 1-5 below).
- **How it will be used:** Source of truth for any future "is X built" question.
- **Confidence:** High (read directly).

## GROUP A — Logic gaps between the two executors

### A1. Daily allocation (drawdown scaling, maturity scaling, tilts, reserve) never reaches the rebalancer that places orders

- **Title:** `LiveScheduler` consumes `/portfolio/state`, not `/portfolio/daily-allocation`.
- **Explanation:** The portfolio service builds two different things. `build_portfolio()` returns base risk-parity
  weights (inverse-vol or HRP, normalized, capped at `max_per_strategy_weight=0.3`). `compute_daily_allocation()`
  layers regime / outcome / confidence tilts, `_drawdown_action_multiplier` (ok 1 / halve .5 / flat 0 / halt 0),
  `_maturity_capital_multiplier`, `reserve_fraction`, hysteresis, and `not_funded` records on top, yielding
  `deployable_equity`. The only automatic order-placing consumer, `LiveScheduler._fetch_portfolio`, calls
  `/portfolio/state` (= `build_portfolio()`), multiplies the weights by full account equity, and trades. No code in
  `vinu-live` or `vinu-agent` calls `compute_daily_allocation` / `/portfolio/daily-allocation` (only comments and the
  CLI). `how-system-implemented.md` §12 and vision A11 present the tilted, scaled result as what sizes live capital.
- **Evidence:** `scheduler.py:465-468` (`GET .../portfolio/state`); `vinu-portfolio/server/app.py:43-45`
  (`/state` → `build_portfolio()`) vs `:56-58` (`/daily-allocation`); grep of `vinu-live/` and `vinu-agent/vinu_agent/`
  for `daily-allocation|compute_daily_allocation` finds no executing caller; `service.py:342-353` (weights normalized
  then capped; no equity scaling in this path).
- **Where found:** `vinu-live/vinu_live/scheduler.py:465`, `vinu-portfolio/vinu_portfolio/server/app.py:43-58`,
  `vinu-portfolio/vinu_portfolio/service.py:294-370, 880-928, 992+`.
- **Solution:** Decide the contract first. Option A: scheduler calls `/portfolio/daily-allocation` and uses its
  `weights` and `deployable_equity`. Option B: move the multipliers into `build_portfolio` so `/state` is already
  scaled. Option C: keep `/state` raw but have the scheduler multiply by a `deployable_fraction` fetched from
  `/portfolio/risk/status`. Recommend A (smallest change, tilts already tested), behind an opt-in flag, fail-open
  to today's behavior.
- **What it will achieve:** The drawdown "halve" step, maturity capital gating, reserve and hysteresis stop being
  computed-and-discarded and actually bound real orders. Closes the v1 pattern #3 "computed then discarded" on the
  highest-stakes path.
- **How it will be used:** Scheduler cycle reads allocation once per cycle; consultation recorded in
  `MaturityConsultationStore`.
- **Confidence:** High on the wiring fact. Mitigating context: `maturity_capital_gating_enabled` defaults `False`
  and `reserve_fraction` defaults `0.0`, so today's defaults would not scale anyway; the drawdown *flat/halt* path is
  still enforced separately by the real kill switch (`_halt_trading`). What is unenforced is **halve**, the maturity
  ladder once enabled, and the tilts.

### A2. Two executors can fight over the same account (overlapping authority, unresolved ownership)

- **Title:** `LiveScheduler` will sell any broker position it does not have a target for, including positions the orchestrator opened.
- **Explanation:** `SignalTranslator.translate` loops over **all broker positions** and emits a full-close instruction
  for any symbol not in `target_weights` (`current_positions` comes from `/agent/broker/positions`, account-wide).
  The orchestrator opens positions for ACTIVE `trade_plan` artifacts into its own book. The scheduler runs every
  3600 s (`vinu-live-worker --interval 3600`) and only skips when its target list is entirely empty. Whenever the
  portfolio has any strategy at all, a trade-plan position in a symbol that is not in the portfolio's target list is
  sold at the next scheduler cycle, then the orchestrator reconciles its book to the broker. Where symbols do overlap,
  two sizing authorities (risk-parity weight x equity vs. risk-band Kelly cap) target the same position.
- **Evidence:** `signal_translator.py:108-117` (held-but-absent → target 0.0, built against account-wide positions);
  `scheduler.py:157-160` (skips only if no weights), `:162-169`; `entrypoint.sh` (both workers); portfolio
  `_list_llm_strategies_in_process` lists all ACTIVE artifacts with no type filter (`service.py:191-203`) while the
  orchestrator reads `type=trade_plan` (`orchestrator.py:1082`).
- **Where found:** as above.
- **Solution:** A design decision, not a patch. Options: (1) symbol ownership registry: each symbol belongs to one
  executor and the other must ignore it; (2) scheduler restricts `current_positions` to symbols it manages
  (its target list ∪ live_decision open positions) instead of the whole account; (3) retire one path. Recommend (2)
  first: smallest change, removes the unconditional liquidation hazard, keeps both paths.
- **What it will achieve:** Removes the possibility of an unplanned liquidation of positions another path opened;
  makes P&L attribution per executor meaningful.
- **How it will be used:** `current_positions` filtered by an explicit `managed_symbols` set; unmanaged positions
  logged, never traded.
- **Confidence:** High on the mechanism (code read). **Unknown from code alone** whether real deployments hold both
  populations at once — if the portfolio's ACTIVE strategies and the trade-plan symbols are always the same set, the
  hazard is latent rather than live. Needs one check on a running deployment.

### A3. Weights-path positions have no stop, invalidation or time-stop

- **Title:** Positions opened by `LiveScheduler` carry no per-position protection; the orchestrator's do.
- **Explanation:** Orchestrator entries submit a broker-side backstop stop (`stop_loss_price`), then run invalidation,
  contingency, trailing-stop and time-stop rules every cycle. `LiveScheduler._execute_plan` posts only
  symbol / side / qty / order_type / client_order_id / optional limit price, and has no per-position evaluation after
  that. For live-decision positions the only exit mechanism is the LLM review every 5 bars (HOLD / EXIT) plus
  portfolio-level halts. The vision asks for risk per trade from stop distance and for thesis-level invalidation plus a
  time stop on every position.
- **Evidence:** `scheduler.py:659-670` (payload fields); `orchestrator.py:1359-1365, 1421-1424` (backstop stop);
  `orchestrator.py:94` (`MAX_HOLD_DAYS` time stop).
- **Where found:** as above.
- **Solution:** For live-decision positions, store `stop_pct` / `max_hold_bars` with the open-position row (strategy
  config fields, defaulted off) and have the poller's review mode treat a breach as an EXIT that does not need the
  LLM. Pure rule, same shape as the orchestrator's.
- **What it will achieve:** Gives the weights path the same floor of protection as the plan path.
- **How it will be used:** Poller checks stop / age every candle close before invoking the agent.
- **Confidence:** High.

### A4. Guard parity: the scheduler path got only part of the "execution unification"

- **Title:** Spread, event blackout and routing were shared; cooldown, freshness, turbulence, stale-signal, CVaR, outage were not.
- **Explanation:** `scheduler.py` imports `EVENT_BLACKOUT_HOURS`, `MAX_SLIPPAGE_PCT`, `MAX_SPREAD_BPS`,
  `PASSIVE_LIMIT_OFFSET_BPS`, `_choose_entry_order_type` from the orchestrator and nothing else. It has no
  consecutive-loss cooldown, no data-freshness guard (its prices are `bars[-1]` of a 1d fetch with no age check,
  yet live-decision trades come from 15m candles), no turbulence pause, no broker-outage pause, no CVaR gate.
- **Evidence:** `scheduler.py:39-45` (the only imports from the orchestrator); `:495-520` (`_fetch_prices`, no
  timestamp check); orchestrator guards at `:99-145`, `:227-237`, `:644-661`, `:1160-1205`.
- **Where found:** as above.
- **Solution:** Extract the guards into `trade_plan/guards.py` (already the shared module) as pure functions and call
  them from both paths, **entries only**. Prioritize data-freshness and cooldown.
- **What it will achieve:** One guard policy instead of two drifting copies; no trades on stale marks.
- **How it will be used:** Scheduler skips new-exposure instructions when a guard fires; exits unaffected (see A5).
- **Confidence:** High.

### A5. Exits are not exempt from halts and gates on the scheduler path

- **Title:** A breaker HALT, kill switch, earnings blackout or wide spread blocks the scheduler's sells as well as its buys.
- **Explanation:** In the orchestrator, exits are `reduce_only` and every guard says "ENTRIES ONLY". In
  `LiveScheduler`: a breaker HALT skips all order planning that cycle; `_execute_plan` returns `[]` on any halt and
  breaks mid-plan on a mid-run halt; the spread gate and the event blackout skip any slice regardless of side; and
  orders carry no `reduce_only` flag, so the agent-side OrderGuard cannot apply its reduce-only exemption either.
  A live-decision EXIT, a weight cut, or a rebalance sell during a halt, inside 24 h of earnings, or in a wide spread
  is therefore delayed until the condition clears. This contradicts the claim in `01-freqtrade.md` ("always exempt
  risk-reducing orders so a halt never traps you") — true for the orchestrator, not for this path.
- **Evidence:** `scheduler.py:177-184` (HALT skips everything), `:587-590` and `:698-704` (halt returns / breaks),
  `:611-634` (gates apply to every slice), `:659-665` (no `reduce_only` in payload); OrderGuard exemption exists at
  `vinu-agent/vinu_agent/broker/order_guard.py:197, 276-280`.
- **Where found:** as above.
- **Solution:** Mark an instruction as reducing when `abs(target_qty) < abs(current_qty)` (same sign), pass
  `reduce_only=True`, and bypass spread/event/halt-skip for those slices (halt policy `entries_only`, already the
  orchestrator's default). Never bypass for increases.
- **What it will achieve:** A halt or event cannot trap an unwanted position on this path.
- **How it will be used:** `SignalTranslator` sets `reduces_exposure` on each `OrderInstruction`; the plan carries it.
- **Confidence:** High on the mechanism. Needs your go-ahead (live-money behavior change).

### A6. Breaker daily-loss is realized-only, and the scheduler path never writes the book it checks

- **Title:** `check_limits()` reads a book the scheduler does not populate, and measures realized loss only.
- **Explanation:** `_check_daily_loss` uses `daily_realized_pnl` from the trade-plan book's closed positions; open
  drawdown does not count. `LiveScheduler._check_breaker` passes that same book, but the scheduler only *reads* it —
  its own orders are recorded nowhere in it (the single `open_position` it calls writes to the separate
  `live_decision` store). So for scheduler cycles, position-count, leverage and cluster checks run over the
  orchestrator's positions, not the ones about to be traded, and daily loss only sees plan-path closures.
  Partial cover exists elsewhere: the portfolio drawdown monitor is equity-based (halts at -20% by default,
  5-minute poll), and OrderGuard has its own risk-budget tiers. Neither is a per-day equity loss limit at the
  breaker's stated threshold.
- **Evidence:** `breaker/engine.py:25-37` (realized only), `:155` (reads book positions); `scheduler.py:95, 256-273`;
  grep of scheduler for book writes finds only reads (`:258, :261, :265`).
- **Where found:** as above.
- **Solution:** Source `daily_pnl` and exposure from the broker account (equity vs. start-of-day equity, positions
  from `/agent/broker/positions`) for the scheduler path, keeping the book for the orchestrator. Add unrealized to the
  daily-loss test.
- **What it will achieve:** The breaker measures what the account actually did today, on both paths.
- **How it will be used:** `check_limits` takes explicit `positions` / `daily_pnl`; each executor supplies its own.
- **Confidence:** High on the facts; the size of the hazard depends on how much the drawdown monitor already covers.

## GROUP B — Decision-logic issues

### B1. One LLM-stated number is counted three times and never recalibrated

- **Title:** `forecast.confidence` is a confluence signal, the EV win-probability, and a sizing scale — raw.
- **Explanation:** The vision's point A4 is "confidence is not P(win)". In code, `forecast.confidence` (stated by the
  forecast LLM) enters (1) the confluence ledger as a supporting / contradicting "signal" with strength = confidence
  (`trade_plan_authoring.py:634-646`), (2) the Trade Score EV term as P(win) (`trade_score_gate.py:74`), and (3) the
  live size scale (`orchestrator.py:1279-1287`, floor 0.5) plus `_derive_entry_decision` (>= 0.5). The three are not
  independent evidence. The only recalibration is after the fact (Brier / accuracy in the calibration gate), with no
  mapping from stated confidence to realized hit-rate applied before EV; `brier_mean` is computed and ignored by
  every decision (v1 A7).
- **Evidence:** lines above; `forecast_skill.py:50-130` (Brier computed, used as a pass/fail gate only).
- **Where found:** as above.
- **Solution:** Keep it as one input. (a) Remove the "forecast_confidence" entry from the confluence ledger, or give
  it zero weight there. (b) Add a reliability map (stated confidence bucket → realized hit-rate from
  `calibration_entries`) with a minimum-sample guard, used in the EV term; fall back to raw confidence below the
  sample floor. Log-only first.
- **What it will achieve:** EV reflects what stated confidence has historically meant; the score's "confluence" regains
  independence.
- **How it will be used:** `_ev_score` takes `calibrated_confidence`; reasons list shows raw vs calibrated.
- **Confidence:** High on the triple use. Whether it matters in practice depends on how well the LLM's confidence is
  already calibrated — unknown until live rows exist.

### B2. Trade Score fail-open defaults can approve a plan whose risk band was never computed

- **Title:** Missing `risk_state` produces a zero `RiskBand`, which passes the Trade Score with inflated EV.
- **Explanation:** `_build_risk_band` returns `RiskBand()` (all zeros) when `risk_state.status != "ok"`.
  `_reward_risk_ratio` then returns `None` (veto skipped), `_risk_score` returns a neutral half score, and
  `_ev_score` sets `expected_loss = 0`, so EV = confidence × magnitude − cost, with no loss term. The plan can be
  approved and become ACTIVE. It cannot actually enter (`orchestrator.py:1208-1211` skips when
  `max_position_size_pct <= 0`), so the harm is an inert ACTIVE plan that occupies a portfolio slot and may receive a
  risk-parity weight in the scheduler path (see A1/A2), not a bad trade.
- **Evidence:** `trade_plan_authoring.py:432-433`; `trade_score_gate.py:73-75, 86-89, 123-126`;
  `orchestrator.py:1208-1211`.
- **Where found:** as above.
- **Solution:** Fail closed at approval: `approve_trade_plan` rejects a plan whose `risk_bands.expected_drawdown` and
  `cvar_95_limit` are both 0 (reason `risk_not_computed`), the same way it already rejects missing calibration
  history. One test per spelling.
- **What it will achieve:** The hard R:R floor cannot be bypassed by a data hole.
- **How it will be used:** Approval gate reason string; shows in `evaluation-status`.
- **Confidence:** High.

## NEW ITEM A7 (found 2026-10-03 while writing the fail-open matrix)

### A7. A failed broker-equity read sizes orders on an invented $1,000,000

- **Title:** `LiveScheduler._fetch_portfolio_value` falls back to a placeholder capital figure when the account read fails.
- **Explanation:** Every other failed read about the account either aborts the cycle (`_fetch_portfolio`, `_fetch_positions` raise) or
  skips the symbol (no price). Equity does neither: an HTTP error, a non-200 reply, or `configured: false` all fall through to "sum of
  positions x price if > 0, else `fallback_portfolio_value`" (default **1,000,000**), logged as a warning. On a flat account with a
  transient `/agent/broker/account` failure, target weights are multiplied by $1M, not the real equity. `configured: false` (no
  broker at all) is a legitimate reason to use a placeholder; an error reading a configured broker is not. OrderGuard's mandate
  limits are the only remaining backstop.
- **Evidence:** `scheduler.py` `_fetch_portfolio_value` (try/except that only logs, then the positions-value / fallback branches);
  `config.py` `fallback_portfolio_value: float = 1_000_000.0`.
- **Where found:** `vinu-live/vinu_live/scheduler.py`, `vinu-live/vinu_live/config.py`.
- **Solution:** distinguish the two cases. Use the fallback only when the reply explicitly says `configured: false`; on an exception
  or non-200 from a configured broker, raise so the cycle aborts exactly like the portfolio and positions fetches do. Keep the
  fallback value configurable for the no-broker paper setup.
- **What it will achieve:** a flaky account read stops being able to size a rebalance on imaginary capital.
- **How it will be used:** same abort path the cycle already has; logged once per aborted cycle.
