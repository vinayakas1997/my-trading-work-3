# Phase 9 — Shadow/Paper Validation & Continuous Re-Validation ("Stage 4")

Status: **not started** · Depends on: Phase 5 · Blocks: —
(Advanced vision — see [02-advanced-vision.md](02-advanced-vision.md))

## What it is

Closes the biggest structural gap in the base pipeline: everything in Phases 1–6 produces a
**static, one-time** judgment — a strategy is validated, refined, compared, and documented
once, at promotion time. Nothing checks whether it actually behaves as predicted once it's
trading, and nothing watches for the edge decaying over time. This phase adds two related
pieces:

**9a — Shadow/paper validation before real capital.** After Stage 3's playbook is produced,
require a paper-trading period (N days/weeks, configurable) where the strategy's signals are
tracked but not traded with real capital. Compare realized paper performance (fills, slippage,
timing) against what the backtest predicted. Only allow promotion to real capital once
live-vs-backtest divergence is within a documented tolerance. `vinu-agent`'s existing
`shadow-account` skill already documents a "trade journal backtesting" methodology
(extract trades → normalize → reconstruct P&L → simulate what-ifs → render shadow P&L report)
that's directly applicable here — this phase operationalizes that methodology into code rather
than leaving it as agent-guided manual analysis.

**9b — Continuous re-validation / decay detection.** Once live, periodically (e.g. monthly) re-run
Stage 0's Monte Carlo validation on a rolling recent window of the strategy's actual live
trades, not just the original backtest. If the validation verdict degrades (p-value rising,
consistency dropping), flag the strategy for review or automatic demotion — the same gate that
guards entry should keep watching after entry.

## Impact

**Before this phase:** A strategy is judged once, at the moment of promotion, using only
backtest data. If market conditions shift and the edge decays, there is no automated mechanism
to detect it — someone has to notice manually, likely after losses have already accumulated.

**After this phase:** A strategy earns real capital only after demonstrating its backtest-
predicted behavior holds in a live paper environment, and continues to be automatically
re-checked afterward — turning the pipeline from "we validated a hypothesis once" into "we
know this makes money and we'll know when it stops."

## Where changes occur

- New module, likely `vinu-live/vinu_live/shadow_validation.py` (`vinu-live` already exists as
  a package — confirm its current scope before adding) or extending the existing
  `shadow-account` skill's methodology into executable code: track live/paper signals
  generated by a promoted strategy, compare against backtest-predicted trade timing/sizing/P&L.
- Storage: a new table (likely in whatever storage `vinu-live` already uses, or a new one)
  recording paper-trading results per strategy per day, and the live-vs-backtest divergence
  metric over time.
- Promotion gate: extend the approval flow (`vinu-research/vinu_research/service.py`, lines
  ~229-260) or add a downstream gate before a strategy is eligible for real-capital trading —
  requiring a completed, passing shadow period.
- Continuous re-validation: a scheduled job (check `vinu-research/vinu_research/vinu_research/scheduled/`,
  which already exists as a directory, for the existing scheduling pattern to follow) that
  periodically re-runs Phase 1's validation functions against a rolling window of a live
  strategy's actual realized trades (not the original backtest trades), and writes the result
  to the same `validation`-shaped storage Phase 1 established, tagged as `revalidation` rather
  than `initial`.
- Alerting/demotion: when re-validation fails, flag in whatever the team's existing
  alerting/monitoring surface is (check `logs/`, `vinu-agent`'s tool surface, or `vinu-live` for
  an existing pattern before inventing a new channel).

## How to test it

- Unit test: given a synthetic paper-trading log that closely matches backtest predictions,
  the divergence metric should be low and the strategy should clear the shadow gate.
- Unit test: given a synthetic paper-trading log that diverges significantly (e.g.
  systematically worse fills, different trade timing), the divergence metric should be high and
  the gate should not clear.
- Unit test: re-validation on a rolling window of live trades that no longer shows the original
  statistical significance should produce a failing verdict and trigger the flag/demotion path.
- Integration test: full lifecycle — promote a strategy, run it through a simulated shadow
  period, confirm it clears to "live-eligible," then feed in a later window of degraded
  synthetic performance and confirm the scheduled re-validation job flags it.
