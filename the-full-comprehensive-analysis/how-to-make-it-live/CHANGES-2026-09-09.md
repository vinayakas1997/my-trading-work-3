# Stage 1 — What Actually Changed, 2026-09-09

This file is the record of real code changes made to `vinu-components` in this
session, written so someone with no context on this conversation can understand
what happened, why, and how to check it themselves. It corresponds to "Stage 1" in
`how-to-make-it-live.md`.

All changes were verified against the existing test suite (`pytest`) with no
regressions — see "How this was verified" at the bottom.

## 1. CVaR tail-risk gate + dynamic vol targeting — the flags were *dead*, not just off

> **Correction, later on 2026-09-09.** The first version of this section claimed the
> only work needed was flipping two `.env` flags, and that the controls were "wired
> into the real order path via `risk_gatekeeper_hook.py`." Both statements were wrong.
> A re-audit found the `.env` edit had never actually been applied *and* that flipping
> the flags alone would have done nothing, because **no caller on any live path ever
> passed `cvar_95` / `current_vol` to `compute_position_size()`**. This section now
> records the real fix.

**Files:** `vinu-research/vinu_research/models.py`,
`vinu-research/vinu_research/trade_plan_authoring.py`,
`vinu-live/vinu_live/trade_plan/orchestrator.py`, `vinu-components/.env`,
`vinu-components/.env-example` (+ tests in `test_trade_plan_authoring.py`,
`test_trade_plan_orchestrator.py`).

### What was there before

`vinu-agent/vinu_agent/agent/position_sizing.py` had a complete, tested
implementation of two controls:
- `cvar_exceeds()` — blocks sizing to zero when 95% CVaR exceeds a threshold.
- `vol_target_scale()` — scales size by `target_vol / current_vol`.

`compute_position_size()` accepts `cvar_95`, `current_vol`, `cvar_enabled`,
`vol_target_enabled` and the gate logic is real. But every caller:
- `ComputePositionSizeTool` (the LLM sizing tool) — its parameter schema has **no**
  `cvar_95` / `current_vol` fields, so the LLM cannot supply them.
- `risk_gatekeeper_hook.py`'s deterministic recompute — passes 9 arguments, **none**
  of them `cvar_95` / `current_vol`.
- `vinu-live/trade_plan/orchestrator.py`'s `_maybe_enter()` — the one place a live
  TradePlan's entry size is actually decided — does **not call
  `compute_position_size` at all**; it reads `risk_bands.max_position_size_pct` and
  (since Stage 2 #24) the forecast-confidence scale, nothing else.

So `cvar_95` was always `None`, the `cvar_95 is not None` guard was always false, and
the gate never fired regardless of the flag. Same for vol targeting. The data *was*
computed upstream — `fetch_risk_state()` produces `cvar_95_daily` and
`daily_volatility` — but `_build_risk_band()` discarded both.

### The fix

Mirror the exact pattern Stage 2 #24 used for forecast confidence: freeze the number
onto the plan at authoring time, read it at `_maybe_enter()`.

1. **`vinu-research/vinu_research/models.py`** — `RiskBand` gained `cvar_95_limit:
   float = 0.0` and `daily_vol: float = 0.0` (positive daily fractions; `0.0` = not
   computed → control skipped). Defaults keep `RiskBand(**old_dict)` in
   `TradePlan.from_json` backward-compatible.
2. **`vinu-research/vinu_research/trade_plan_authoring.py`** — `_build_risk_band()`
   now reads `risk_state["cvar_95_daily"]` / `["daily_volatility"]` (already computed
   right there, previously dropped) and passes them to the `RiskBand` constructor.
3. **`vinu-live/vinu_live/trade_plan/orchestrator.py`** — module constants
   `CVAR_GATE_ENABLED` (`VINU_RISK_CVAR_ENABLED`), `CVAR_THRESHOLD`
   (`VINU_RISK_CVAR_THRESHOLD`, default `0.03`), `VOL_TARGET_ENABLED`
   (`VINU_RISK_VOL_TARGET_ENABLED`), `VOL_TARGET` (`VINU_RISK_VOL_TARGET`, default
   `0.15` annual), plus a local `_vol_target_scale()` (same cross-service-duplication
   note as `_forecast_confidence_scale`; converts the annual target to daily via
   `/ sqrt(252)` so both sides are daily; capped at `1.0` — a calm market does not
   license extra leverage). `_maybe_enter()` now, right after the stale-signal check:
   - **CVaR gate** — if `CVAR_GATE_ENABLED` and `risk_bands.cvar_95_limit >
     CVAR_THRESHOLD`, returns `{"action": "entry_blocked_by_cvar", ...}` and never
     calls the broker. A hard block, not a size tweak — "the tail on this name is too
     fat to open here."
   - **Vol targeting** — after the forecast-confidence scale, multiplies `size_pct`
     by `_vol_target_scale(risk_bands.daily_vol)`.
   Both skip on a missing/`0.0` value (fail-open, same posture as every other
   data-quality guard in the file).
4. **`vinu-components/.env`** — added (this time actually written to the file):
   ```
   VINU_RISK_CVAR_ENABLED=true
   VINU_RISK_CVAR_THRESHOLD=0.03
   VINU_RISK_VOL_TARGET_ENABLED=true
   VINU_RISK_VOL_TARGET=0.15
   ```
   `.env-example` updated to match with an accurate description of where they are read.

### Scope note — what this does *not* cover

The **research/LLM sizing path** (`ComputePositionSizeTool` +
`risk_gatekeeper_hook.py`) still does not feed `cvar_95` / `current_vol` — that path
sets `approved_size` stored on the artifact at promotion time, not the live order
quantity. Wiring it needs a tool-schema change plus an LLM-prompt change to have the
manager populate `sizing_inputs` with those fields; deferred. The live entry path —
the one that decides how many ETH a real order buys — is covered.

### How to verify

- `grep VINU_RISK vinu-components/.env` now shows all four keys.
- `TestCvarGateAndVolTargeting` in `vinu-live/tests/test_trade_plan_orchestrator.py`:
  a plan with `risk_bands.cvar_95_limit = 0.05` and the gate enabled returns
  `entry_blocked_by_cvar` with `post_mock.call_count == 0`; `daily_vol = 0.03` with
  vol targeting on writes a position with `qty` scaled by
  `(0.15/sqrt(252)) / 0.03 ≈ 0.315`.
- `TestAuthorTradePlan::test_produces_complete_plan` in
  `vinu-research/tests/test_trade_plan_authoring.py` asserts `plan.risk_bands.
  cvar_95_limit > 0` and `daily_vol > 0`.

## 2. Kill switch: exit/reduce orders now survive a halt

This was the highest-severity fix of the three. It closes Scenario 21 from
`seceniors.md`: *"Portfolio drawdown hits -20%, the kill switch engages, and the
system can no longer exit the position that's making it worse."*

### The problem, precisely

There are **two separate halt mechanisms** in the codebase:

1. **`vinu-live`'s local "breaker"** (`orchestrator.py`, `check_limits()`) — computes
   its own drawdown/VaR/exposure limits. This one already had the fix:
   `HALT_POLICY = os.environ.get("VINU_LIVE_HALT_POLICY", "entries_only")` and a
   `_halt_allows_exit()` helper that lets exit/reduce orders through even when this
   local breaker says HALT.

2. **The global filesystem kill switch** (`vinu-agent/vinu_agent/broker/kill_switch.py`,
   `is_trading_halted()`) — this is the one actually engaged by
   `PortfolioDrawdownMonitor` at -20% portfolio drawdown, via `POST /broker/halt`.
   It was checked inside `OrderGuard.check()`
   (`vinu-agent/vinu_agent/broker/order_guard.py`), and **that check ignored which
   side the order was on** — it rejected *everything*, including an order trying to
   close the exact position that triggered the halt in the first place.

So: someone had already fixed this exact problem once, in `vinu-live`'s local
breaker — but the fix never got applied to the global kill switch, which is the one
that matters most, because it's the one tied to the actual -20% circuit breaker. An
exit order that passed the local breaker's check would still get rejected two layers
later by `OrderGuard`.

### The fix

Added a `reduce_only: bool` flag that flows through the entire order path, and gave
`OrderGuard.check()` the same policy-driven exemption `vinu-live`'s local breaker
already had — reusing the **same environment variable**
(`VINU_LIVE_HALT_POLICY`, default `entries_only`) so there is one policy knob, not two
that could silently disagree.

**Files changed, in call order:**

1. **`vinu-agent/vinu_agent/broker/order_guard.py`**
   - Added `_halt_policy_allows_reduce_only()` — reads `VINU_LIVE_HALT_POLICY`.
   - `OrderGuard.check(..., reduce_only: bool = False)` — when the kill switch is
     engaged AND `reduce_only=True` AND the policy allows it, the order is let
     through (logged as a warning, not silently) instead of rejected.
   - `OrderGuard.pre_approve(..., reduce_only: bool = False)` — this is the *second*
     check that runs immediately before actual submission (inside the kill-switch
     lock); it delegates to `check()`, so without this change an exit could pass the
     first check and still get rejected here.

2. **`vinu-agent/vinu_agent/tools/trade_tool.py`**
   - `TradeTool`'s tool schema gained a `reduce_only` parameter (so the LLM agent can
     mark its own exit orders, for Stage 5 work later).
   - `execute()` reads `kwargs.get("reduce_only", False)` and passes it to both
     `guard.check()` and `guard.pre_approve()`.

3. **`vinu-agent/vinu_agent/server/routes_broker.py`**
   - `OrderRequest` (the HTTP schema for `POST /broker/order`, used by both the LLM's
     tool and vinu-live's own order placement) gained `reduce_only: bool = False`.

4. **`vinu-live/vinu_live/trade_plan/orchestrator.py`**
   - `_submit_order(..., reduce_only: bool = False)` — now sends `reduce_only` in the
     HTTP payload to `/agent/broker/order`.
   - Four call sites that are genuinely risk-reducing now pass `reduce_only=True`:
     - the 50%-at-1R bracket take-profit
     - the capital-allocator-requested rebalance reduce
     - the invalidation exit (full close)
     - the contingency-rule partial reduce
   - The one call site that opens a **new** position (the entry path) was left as
     `reduce_only=False` (the default) — an entry must never bypass a halt.

**Why the distinction matters:** a naive fix ("just let all `sell` orders through on
halt") would have been wrong — going short is a `sell` order that *increases* risk,
not reduces it. `reduce_only` is set by the caller based on what the order is actually
doing (closing/shrinking an existing position), not inferred from `side` alone.

**How to verify:** with the kill switch engaged (`POST /broker/halt`), an order with
`reduce_only=true` should now return `status: submitted` (or fail for an unrelated
reason) instead of `status: rejected, reason: "Trading is halted by kill switch"`. An
entry order (`reduce_only` omitted or `false`) should still be rejected exactly as
before.

## 3. Bonus fix: idempotency keys were computed but silently dropped

This wasn't on the Stage 1 list — it was found while tracing the exact request path
for fix #2 above, because `_submit_order()`'s payload-building code was sitting right
next to the `client_order_id` logic.

### The problem

`orchestrator.py`'s `_submit_order()` already computed a `client_order_id`
(`artifact+symbol+side+qty+minute-bucket`) meant to let Alpaca de-duplicate a retried
order server-side — this was Scenario 27 in `seceniors.md`, previously rated "fixed,
8/10." That rating was wrong. The key was:

1. Computed correctly in `orchestrator.py`.
2. Sent as `payload["client_order_id"]` to `POST /agent/broker/order`.
3. **Silently dropped** — `OrderRequest` (the Pydantic schema for that endpoint) had
   no `client_order_id` field, and Pydantic ignores unrecognized fields by default. So
   it never reached `TradeTool.execute()`.
4. Even if it had reached `TradeTool.execute()`, neither `Broker.submit_order()`
   (the interface) nor `AlpacaBroker.submit_order()` (the implementation) accepted a
   `client_order_id` parameter to forward to Alpaca's actual API.

So the idempotency protection was computed, sent, and then discarded at every
remaining step. A retried order would not have been deduplicated by Alpaca at all.

### The fix

Plumbed `client_order_id` all the way through:

- **`vinu-agent/vinu_agent/broker/base.py`** — `Broker.submit_order()` interface
  gained `client_order_id: str | None = None`.
- **`vinu-agent/vinu_agent/broker/alpaca.py`** — `AlpacaBroker.submit_order()` now
  accepts it and includes it in the payload sent to Alpaca's `/v2/orders` endpoint
  (`payload["client_order_id"] = client_order_id` when set) — this is the field
  Alpaca itself uses server-side to reject a duplicate submission.
- **`vinu-agent/vinu_agent/server/routes_broker.py`** — `OrderRequest` gained
  `client_order_id: str | None = None`.
- **`vinu-agent/vinu_agent/tools/trade_tool.py`** — `execute()` reads
  `kwargs.get("client_order_id")` and passes it to `broker.submit_order()`.

**How to verify:** submit two orders with the same `client_order_id` in quick
succession against a real (or sandbox) Alpaca account — the second should be rejected
or return the same order as the first, not create a duplicate position.

## 4. Correction (not a code change): ShadowEvaluator was already scheduled

Earlier in this analysis, Scenario 18 ("ShadowEvaluator built but never called on a
schedule") was verified as still open by checking `vinu-live/vinu_live/scheduler.py`
for a reference to `ShadowEvaluator` and finding none.

That check was incomplete. `scheduler.py` is the portfolio-rebalance cycle file — it
was never going to call `ShadowEvaluator`. The actual scheduled caller lives in
`vinu-live/vinu_live/cli.py`'s `shadow_worker_main()`, a complete
`while True: evaluate_all(); sleep(interval)` loop, and it's started automatically by
`vinu-live/entrypoint.sh`:

```bash
vinu-live shadow-worker &
```

This runs as a background daemon alongside the other three real workers
(`vinu-live-worker`, `trade-plan-worker`, `feedback-worker`) every time the `live-api`
container starts. No code change was needed — the earlier "still open" verdict for
Scenario 18 has been corrected in `seceniors.md`.

**Lesson for future verification passes on this codebase:** check `entrypoint.sh` /
`Dockerfile` for what a service actually starts, not just the most obviously-named
file — a background worker's scheduling can live in the container startup script
rather than in the module that defines the worker.

## 5. (Stage 2) Risk budget: computed correctly, never enforced, and never actually accumulated

This closes Scenario 22 from `seceniors.md`: *"A symbol hits -3% daily P&L (TIER_HALT).
`compute_risk_budget()` correctly says stop. The next order for that symbol goes
through anyway, because nothing ever asked."*

### Problem 1 — never enforced

`vinu-portfolio/vinu_portfolio/risk_budget.py`'s `compute_risk_budget()` was already
correct: it computes a 3-tier status per symbol (warning at -1% daily P&L, reduce at
-2%, halt at -3%, all as a fraction of equity) and a `suggested_size_multiplier`. It's
exposed over HTTP at `GET /portfolio/risk/status`. But nothing ever called that
endpoint from the order path — `OrderGuard` (`vinu-agent/vinu_agent/broker/
order_guard.py`) had no knowledge of it at all. The number was correct and simply
never read.

### Problem 2 — even if read, it wouldn't have accumulated

Separately, `vinu_portfolio/service.py`'s `compute_risk_status()` (the method behind
that endpoint) built a **fresh `DailyPositionTracker()` on every single call**:

```python
tracker = DailyPositionTracker()
budget = compute_risk_budget(positions, equity, regime=regime, tracker=tracker)
```

`DailyPositionTracker.record_daily_pnl()` is designed to accumulate across calls
within the same UTC day — but a fresh instance means every call starts from zero. So
even a live symbol that had genuinely lost -5% intraday across several polls would
never cross the -3% halt threshold in this function's eyes, because each call only
ever saw that one call's `unrealized_pl` snapshot, not the accumulated total. There
was already a test (`test_daily_pnl_does_not_accumulate_across_repeated_calls`) that
explicitly asserted this broken behavior as expected — a real, deliberate record of a
known gap, not an oversight in testing.

### The fix

1. **`vinu-portfolio/vinu_portfolio/service.py`** — moved the tracker onto the
   `PortfolioService` instance: `self._risk_tracker = DailyPositionTracker()` in
   `__init__`, reused by `compute_risk_status()` on every call instead of being
   recreated. `server/app.py` constructs `PortfolioService` exactly once per process
   (`_service = PortfolioService()` inside `create_app()`, closed over by every route
   handler), so this tracker now genuinely persists for the life of the process —
   resetting only at UTC midnight, via `DailyPositionTracker`'s own internal
   `_check_reset()`.
2. **`vinu-portfolio/tests/test_risk_budget.py`** — the test that asserted the broken
   behavior was rewritten (`test_daily_pnl_accumulates_across_repeated_calls`) to
   assert the correct one: two calls in the same day now show `500.0` then `1000.0`,
   not `500.0` twice.
3. **`vinu-agent/vinu_agent/broker/order_guard.py`** — added
   `_check_risk_budget(symbol, side)`, called from `check()` for any order that is
   **not** `reduce_only`. It calls `/portfolio/risk/status`, finds the entry for the
   order's symbol, and rejects the order if `halted` is true — with the exact
   TIER_HALT percentage in the rejection reason. Follows the same conventions as the
   existing `_check_portfolio_concentration`: fails open (logs a warning, allows the
   order) if the portfolio service is unreachable or errors.
4. **Why `reduce_only` matters here too**: the entire point of TIER_HALT is to stop a
   losing symbol from digging deeper — it must never block an order that's *shrinking*
   exposure on that symbol. Reusing the same `reduce_only` flag from the Scenario 21
   fix meant this didn't need new plumbing — it was already flowing through
   `OrderGuard.check()`/`pre_approve()` from the kill-switch fix.
5. **`vinu-agent/tests/test_order_guard.py`** — added a new `TestRiskBudget` class (5
   tests: blocks a halted symbol, allows a non-halted one, `reduce_only` bypasses a
   halted symbol, fails open on a lookup error, ignores other symbols' halted status).
   Also updated two pre-existing tests in `TestPortfolioConcentration`
   (`test_sell_orders_are_never_blocked`, `test_disabled_by_default_skips_call`) that
   had asserted `requests.get` was *never* called in those scenarios — that assumption
   was specific to the concentration check being skipped, and is no longer true now
   that the risk-budget check legitimately calls a different endpoint in those same
   scenarios. Narrowed both assertions to check the concentration-specific URL
   (`/portfolio/state`) wasn't called, rather than that no HTTP call happened at all.

**What this does *not* do:** hitting TIER_HALT on a symbol still doesn't escalate to
the global kill switch (`halt_trading(scope=symbol)`) — it only stops `OrderGuard`
from approving new orders for that symbol going forward. That's a narrower fix than a
full auto-halt, but it's sufficient to close the specific failure mode in Scenario 22
(an order for an already-halted symbol going through because nothing checked).

**How to verify:** with a symbol's daily P&L pushed past -3% of equity (via two or
more calls to `/portfolio/risk/status` in the same day, or directly constructing a
`RiskBudget` with `halted: true`), a subsequent non-`reduce_only` order for that
symbol through `TradeTool`/`POST /broker/order` should return `status: rejected,
reason: "... is at risk-budget TIER_HALT ..."`. A `reduce_only: true` order for the
same symbol should still succeed.

## 6. (Stage 2) PBO: computed, returned once, then discarded forever

This closes Scenario 19 from `seceniors.md`: *"A research run finds a strategy with
PBO 0.75 — severe overfitting. The run completes. An operator checks the artifact
later. There is no PBO to see; it never made it past the original API response."*

### The problem

`vinu_research/pbo.py` correctly computes Probability of Backtest Overfitting
(combinatorially symmetric cross-validation, Bailey/Borwein/López de Prado) for every
research run, and it was returned in that run's live `ResearchResult.pbo` response —
but that was the end of its life:

- `ResearchRunRecord` (the dataclass persisted to the `research_runs` table) had no
  `pbo` field at all.
- `research_runs`' SQL schema had no `pbo` column — confirmed by reading
  `insert_run`/`update_run` directly.
- `Artifact` (the dataclass persisted to the `artifacts` table, and the one
  `promotion.meets_promotion_bar()` actually reads) had no `pbo` field either.
- `promotion.py`'s promotion gate checked deflated Sharpe, the holdout result, and the
  stress test — never PBO, because there was nothing to check.
- Both read endpoints that expose a run/artifact over HTTP (`GET /research/runs/{id}`
  and the artifact-list endpoint) never returned `pbo`, independent of persistence —
  the dict they build is manually enumerated field-by-field and `pbo` was simply
  missing from both lists, same shape of bug as the persistence gap itself.

So a strategy with severe overfitting (PBO 0.75) would clear promotion exactly as
easily as one with PBO 0.1 — the number was real and correctly computed, and every
single consumer of it was blind to it.

### The fix

Threaded `pbo` through every layer PBO needed to reach, mirroring the exact pattern
already used for `holdout_passed`/`stress_test_passed` at each step:

1. **`vinu-research/vinu_research/storage/models.py`** — `ResearchRunRecord.pbo:
   float | None = None`. Also added to `to_dict()` (this dict is manually enumerated,
   not derived from `dataclasses.asdict`, so it needed its own explicit key — this is
   the same class of bug as the two read endpoints below, just one level lower).
2. **`vinu-research/vinu_research/storage/sqlite_backend.py`** — `research_runs` gets
   a `pbo REAL` column (added to the fresh-create schema, plus a
   `_MIGRATIONS` entry so existing databases pick it up on next connect, same
   idempotent-by-name mechanism as every other column added this way in this file);
   `insert_run`/`update_run`/`_row_to_record` all updated to read/write it.
3. **`vinu-research/vinu_research/models.py`** — `Artifact.pbo: float | None = None`.
4. **`vinu-research/vinu_research/storage/strategy_store.py`** — same treatment as
   `sqlite_backend.py` but for the `artifacts` table: schema, migration list,
   `upsert_artifact`, `_row_to_artifact`.
5. **`vinu-research/vinu_research/service.py`** — `run_research()` now sets
   `record.pbo = result.pbo.get("pbo") if result.pbo else None` immediately next to
   the existing `holdout_passed`/`stress_test_passed` assignment;
   `_create_artifact_from_run()` copies `record.pbo` onto the new `Artifact`, same as
   it already does for those two fields.
6. **`vinu-research/vinu_research/config.py`** — new `promotion_pbo_threshold: float =
   0.7` (matches `sweep_grid.py`'s existing `pbo_severe` constant, used by a related
   but separate sweep-recipe evidence gate) and `promotion_pbo_required: bool = True`,
   both configurable via `VINU_RESEARCH_PROMOTION_PBO_THRESHOLD` /
   `VINU_RESEARCH_PROMOTION_PBO_REQUIRED`.
7. **`vinu-research/vinu_research/promotion.py`** — `meets_promotion_bar()` gained a
   PBO check with the same two-sided shape the holdout/stress-test checks already
   have: reject with a reason if `pbo` is `None` while required (too few splits to
   compute it, treated the same as an uncomputed holdout — a reason to withhold
   promotion, not wave it through), or reject if `pbo > promotion_pbo_threshold`.
8. **`vinu-research/vinu_research/server/routes_read.py`** — both `GET
   /research/runs/{id}` (via the `to_dict()` fix above) and the artifact-list endpoint
   now include `pbo` in their response.

**Why `promotion_pbo_required` defaults to `True`, not `False`:** the whole point of
this fix is to close a silent gap, not add an optional extra. Defaulting to required
matches the precedent already set by `promotion_holdout_required` and
`promotion_stress_test_required`, both `True` by default. The cost is that any
artifact created *before* this fix has `pbo = NULL` in the new column and will be
rejected at promotion time with an explicit "PBO required but was never computed"
reason unless re-approved through a fresh run or the flag is turned off — see "What
this does not do" below.

**What this does *not* do:** no backfill migration for pre-existing rows. An artifact
promoted before this session has no PBO on file and cannot be un-promoted retroactively
— but the *next* promotion decision for any BENCHING artifact will now correctly
require it.

**How to verify:** run `promotion.meets_promotion_bar()` against an `Artifact` with
`pbo=0.8` and default config — the returned `PromotionVerdict.eligible` should be
`False` with a reason mentioning "PBO 0.800 above severe-overfitting threshold". With
`pbo=0.2`, it should pass (holding deflated Sharpe/holdout/stress-test constant). A
round trip through `ResearchStorage.insert_run()`/`get_run()` with `pbo` set should
return the same value back.

## 7. (Stage 2) Forecast confidence: computed for every TradePlan, read by nothing that sizes a trade

This closes Scenario 24 from `seceniors.md`: *"A TradePlan has forecast confidence
0.65. It gets sized at full Kelly. The next day, the same strategy generates a
forecast of 0.52 — barely better than a coin flip. It gets sized exactly the same."*

### The problem

`Forecast.confidence` (a field on every `TradePlan`, set by whatever produced the
plan) existed and was populated, but nothing that actually decides an order's size
ever read it:

- `vinu-agent/agent/position_sizing.py`'s `compute_position_size()` — the general
  Kelly/fixed-fractional/ATR sizing formula — took no forecast input at all.
- `vinu-live/trade_plan/orchestrator.py`'s `_maybe_enter()` — the **real** place a
  live TradePlan's entry quantity gets computed — read only
  `risk_bands.max_position_size_pct` and multiplied straight through to `qty`,
  completely ignoring `plan["forecast"]["confidence"]` sitting right next to it in
  the same dict.

A 0.52-confidence plan and a 0.95-confidence plan produced identical order sizes.

### The fix

Two separate consumers, matching the two real places sizing happens in this
codebase — deliberately not one shared function, since `vinu-agent` and `vinu-live`
are separate deployable services with no shared package for this kind of logic (the
same reason the Scenario 21 kill-switch fix duplicated a small policy check rather
than importing across the service boundary):

1. **`vinu-agent/vinu_agent/agent/position_sizing.py`** — added
   `forecast_confidence_scale(confidence, floor=0.5)`: returns `confidence` itself as
   the multiplier, clamped to `[floor, 1.0]`, or `1.0` (no scaling) if confidence is
   `None` or non-positive. Wired into `compute_position_size()` as a new
   `forecast_confidence` parameter, applied in the same `_apply_vol` pipeline step
   that already chains the CVaR/vol-target adjustments — same shape, same place.
   Gated by `VINU_RISK_FORECAST_SCALING_ENABLED`, **defaulting to `true`** (unlike
   CVaR/vol-target, which shipped disabled — see item 1 above. The reasoning here is
   the same reasoning that led Stage 1 to flip those two flags on: shipping this
   disabled would just recreate the exact "the code exists, the data exists, nothing
   connects them" bug this whole fix closes).
2. **`vinu-live/vinu_live/trade_plan/orchestrator.py`** — added a local
   `_forecast_confidence_scale()` (same formula, duplicated per the cross-service
   note above) and `FORECAST_SCALING_ENABLED`/`FORECAST_SCALING_FLOOR` module
   constants reading the same env var names. `_maybe_enter()` now reads
   `plan.get("forecast", {}).get("confidence")`, computes the scale, and multiplies
   `size_pct` by it **before** computing `qty = (size_pct * portfolio_value) /
   price` — this is the actual production code path that decides how many shares a
   live TradePlan entry buys.

**Why floor at 0.5 instead of scaling linearly to zero:** a forecast confidence of,
say, 0.15 is weak but not "this trade should not happen" — that judgment already
belongs to whatever gate decided the plan was worth generating in the first place
(the promotion bar, `risk_gatekeeper`, etc.). Sizing is not the place to re-litigate
whether to take the trade at all; it's the place to size conviction that's already
been judged worth acting on. A near-zero forecast producing a near-zero, effectively
no-op order would be a confusing silent failure mode — the position "enters" but is
too small to matter, with no rejection reason logged anywhere.

**Test coverage:** `vinu-agent/tests/test_position_sizing.py` gained a
`TestForecastConfidenceScale` class (7 unit tests on the scale function itself) plus
5 integration tests inside `TestComputePositionSize` (scaling direction, floor
behavior, `None`/disabled no-ops, traceability in the returned `inputs` dict).
`vinu-live/tests/test_trade_plan_orchestrator.py` gained a
`TestForecastConfidenceScalesEntrySize` class (4 tests) that runs the real
`_maybe_enter()` path end-to-end and checks the actual `qty` written to the position
book — high confidence ≈ full size, low confidence floored at half, missing forecast
= full size, disabled flag = full size. (Test expectations account for
`vinu_live.book.quantize.qty_float()`'s share-quantity rounding, which was already
in place and unrelated to this fix — a raw `0.05 * 100000 / 150 = 33.33` share
calculation gets rounded to a whole share by the existing book-write path.)

**How to verify:** call `compute_position_size(..., forecast_confidence=0.9)` vs
`forecast_confidence=0.3` with identical other inputs — the 0.3 case should return a
smaller `size`, floored at half of the 0.9 case's implied max, not a ninth of it. For
the live path, construct a `TradePlan`-shaped dict with `risk_bands.
max_position_size_pct` and a low `forecast.confidence`, and confirm the position
opened by `_maybe_enter()` has fewer shares than the same plan with `forecast`
removed entirely.

## 8. (Stage 2) YAML strategies: permanently "not_tracked," now get a real track record

This closes Scenario 20 from `seceniors.md`: *"4 built-in YAML strategies trade live
with zero outcome tracking. They get a permanent neutral (1.0) allocation multiplier
no matter how they perform, forever — there is no feedback loop at all for half the
strategy universe."*

### The problem

`vinu-portfolio/vinu_portfolio/service.py`'s `_fetch_outcome_confidence()` had a hard
`if strategy.get("kind") != "llm_python": return {"source": "not_tracked", ...}` at
the top — YAML strategies never reached any real logic. The reason wasn't laziness:
`llm_python` (`trade_plan`) strategies get their track record from
`calibration_entries`, which are written per closed *position*, keyed by
`artifact_id` — and YAML strategies have neither. They're portfolio target-weight
strategies (risk-parity/rebalancer, run by `vinu-live`'s `LiveScheduler`), not
discrete buy-then-sell trades with an open/close lifecycle. There was genuinely no
existing data source shaped like what `calibration_entries` expects.

### The fix

Rather than inventing a new position-tracking concept for weight-based strategies
(a much larger change, and the wrong shape of fix for something that isn't actually
missing infrastructure so much as missing a formula), this computes a directional
track record from two series `vinu-portfolio` already fetches elsewhere for
correlation purposes:

- The strategy's own historical target-weight series, from its existing
  `weights_source` URL (`GET {strategy_api_url}/strategy/weights/{name}` — the exact
  same endpoint `_fetch_strategy_returns()` already calls).
- The symbol's own price history, via the existing `GET {stock_api_url}/stock/
  candles/{symbol}?interval=1d&adjusted=true` pattern already used by
  `_fetch_symbol_regime()`.

**`vinu-portfolio/vinu_portfolio/service.py`** — added `_fetch_yaml_track_record()`:
for each pair of consecutive dates present in both series, if the strategy held a
non-flat weight on the earlier date, checks whether that weight's sign (positive =
long, negative = short) matches the sign of the symbol's realized return between the
two dates. A flat (near-zero) weight is excluded — it's "no directional call made,"
not scored as a wrong one. `_fetch_outcome_confidence()` now routes `kind == "yaml"`
here instead of the hardcoded return.

Same three-state contract the `llm_python` path already had:
- `"not_tracked"` (accuracy `None`) — weight or price history unavailable/empty,
  same as before. **Never a fabricated number** — this was the existing contract's
  most important promise and it's unchanged.
- `"insufficient_data"` — fewer directional calls than `min_calibration_entries_for_tilt`.
- `"yaml_track_record"` — a real `accuracy` (correct calls / total calls) and
  `n_entries` (total calls), which flows straight into the existing
  `_outcome_confidence_multiplier()` — no changes needed there at all, since it
  already only looks at `accuracy`/`n_entries`, not `source`.

**What this does *not* do:** no dollar P&L tracking, only directional accuracy —
the same thing `trade_plan` calibration already measures, not a new richer metric.
`MetaStorage` (the separate `vinu-strategy` service's own registry, mentioned in the
original gap doc) was deliberately not touched — computing the track record on read
in `vinu-portfolio` avoids needing new write-path logic in a second service for
information `vinu-portfolio` can already derive itself from data it already fetches.

**Test coverage:** `vinu-portfolio/tests/test_service.py` gained a
`TestYamlTrackRecord` class (8 tests) — the accuracy math on a hand-computed 4-day
weight/price series (verified by hand: 3 directional calls, 1 correct, accuracy
1/3), the insufficient-data threshold, an all-flat-weights edge case, and fail-open
behavior on missing/empty/erroring weight or price data. One pre-existing test
(`test_yaml_strategy_always_not_tracked`) was renamed to
`test_yaml_strategy_with_no_symbol_not_tracked` — the blanket claim in its name
stopped being accurate; the specific case it tests (no `symbol`/`weights_source` on
the strategy dict) is still correctly `not_tracked`.

**How to verify:** call `_fetch_outcome_confidence({"kind": "yaml", "symbol": "AAPL",
"weights_source": "..."})` against a real deployment where that YAML strategy has
run long enough to have weight history — the response should show
`"source": "yaml_track_record"` with a real `accuracy` once mocked/real HTTP calls to
the weights and candles endpoints succeed, instead of the previous unconditional
`"not_tracked"`.

## 9. (Stage 2) Signal TTL: TradePlan.created_at existed and was stamped, nothing read it

This closes Scenario 36 from `seceniors.md` (and half of Scenario 9): *"A TradePlan
generated at 9:30am with an entry zone that price never touches is still 'valid'
hours or days later. Nothing ever expires a stale signal."*

### The problem, and a correction of the original claim

The original analysis said Vina had "no `signal_generated_at`, `valid_until`,
`max_age` fields." That was only half right. `TradePlan.created_at`
(`vinu-research/vinu_research/models.py`) already existed as a field, and —
checked directly in `trade_plan_authoring.py`'s `author_trade_plan()` — it was
already being stamped with a real `datetime.now(timezone.utc).isoformat()` at plan
generation time, then persisted into `Artifact.trade_plan_data` by
`freeze_trade_plan()`. The data existed in every real TradePlan in production. What
was actually missing was a consumer: `vinu-live/trade_plan/orchestrator.py`'s
`_maybe_enter()` — the only place that decides whether to act on a plan — read
`direction`, `risk_bands`, `forecast`, but never `created_at`. A plan generated three
days ago and never triggered was exactly as "valid" as one generated three minutes
ago.

### The fix

**`vinu-live/vinu_live/trade_plan/orchestrator.py`**:
- `SIGNAL_MAX_AGE_HOURS = float(os.environ.get("VINU_LIVE_SIGNAL_MAX_AGE_HOURS",
  "72"))` — defaults to 72 hours, chosen to be generous enough not to reject
  legitimate slower-moving daily/swing-timeframe plans while still catching signals
  that are genuinely stale.
- `_signal_age_hours(created_at)` — parses the ISO timestamp, returns hours elapsed,
  or `None` (never blocks) if the field is missing or unparseable — fail-open, same
  posture as every other data-quality-dependent check in this file.
- `_maybe_enter()` now checks this immediately after confirming the plan has a real
  direction, before any of the sizing/breaker/cooldown/turbulence checks: a plan
  older than the threshold returns `{"action": "entry_blocked_by_stale_signal", ...}`
  with the exact age in the reason, instead of falling through to a normal entry.

**Why this also partially closes Scenario 9 (hesitation):** that scenario's
complaint included "no signal time-to-live/expiration" as one of several missing
pieces. This fix closes that specific piece. It does **not** close the rest of
Scenario 9 — real-time hesitation-cost measurement and a proactive "this setup is
aging, decide now" alert are both still absent. Scenario 9 stays marked
PARTIALLY HANDLED in `seceniors.md`, not resolved.

**Test coverage:** `vinu-live/tests/test_trade_plan_orchestrator.py` gained a
`TestSignalAgeBlocksStaleEntry` class (5 tests): fresh signal enters normally, a
100-hour-old signal is blocked (default threshold is 72h), a missing `created_at`
never blocks (fail-open), an unparseable `created_at` never blocks, and the env-var
override (`SIGNAL_MAX_AGE_HOURS = 0.0`) disables the check entirely.

**How to verify:** construct a `TradePlan`-shaped dict with `created_at` set to
100+ hours in the past and call `_maybe_enter()` — it should return
`entry_blocked_by_stale_signal` and never call the broker. The same plan with
`created_at` removed, or set to a recent timestamp, should enter normally.

## 10. (Stage 2) Portfolio-level daily order cap: per-symbol limits existed, nothing capped the total

This closes one of three sub-gaps in Scenario 8 from `seceniors.md`: *"OrderGuard
caps orders at 10/symbol/day. Across 20 traded symbols, that's 200 orders/day with
nothing capping the portfolio-wide total."*

### The fix

- **`vinu-agent/vinu_agent/broker/mandate.py`** — `TradingMandate` gained
  `max_daily_orders_portfolio: int = 0`. The `0` is only the dataclass fallback for
  when no mandate.yaml exists; wired into `load()`'s YAML parsing and `to_dict()`,
  same as every other mandate field.
  **Re-audit 2026-09-09:** the original writeup left this "disabled by default —
  tune per deployment," which meant the cap protected nothing out of the box.
  `vinu-agent/entrypoint.sh`'s seeded mandate.yaml now sets
  `max_daily_orders_portfolio: 50` — a safety net for a ~3-9 symbol universe
  (generous over realistic daily operation, hard stop before a runaway fan-out /
  retry loop becomes hundreds of orders). `reduce_only` orders are exempt, so it
  never blocks de-risking. Still the one knob an operator should retune to their
  actual live symbol count.
- **`vinu-agent/vinu_agent/broker/daily_limits.py`** — `DailyLimitStore` gained

  WHERE date = ?` — the portfolio-wide sum across every symbol traded today, same
  persistent SQLite-backed store the per-symbol counts already use (so it survives
  `OrderGuard` being constructed fresh on every `trade_tool.py` call, same fix

- **`vinu-agent/vinu_agent/broker/order_guard.py`** — `check()` gained a portfolio-
  wide check right after the existing per-symbol one: if
  `mandate.max_daily_orders_portfolio > 0` and the order is not `reduce_only`, and
  `count_today_total() >= max_daily_orders_portfolio`, the order is rejected.
  `reduce_only` orders are exempt — a portfolio-wide overtrading cap must never be
  the thing that stops de-risking on a bad day, same posture as every other
  `reduce_only` exemption added this session (kill switch, risk budget).

**What this does not touch:** Scenario 8 listed three gaps — no portfolio-level
order cap (now fixed), no turnover cap (a percentage-of-portfolio metric, distinct
from raw order count — untouched), and no transaction-cost integration in sizing
(money-gate gap #2 territory — untouched). Scenario 8 stays marked PARTIALLY
HANDLED, not resolved, in `seceniors.md`.

**Test coverage:** `vinu-agent/tests/test_daily_limits.py` gained a
`TestCountTodayTotal` class (3 tests). `vinu-agent/tests/test_order_guard.py` gained
a `TestPortfolioDailyOrderCap` class (4 tests): disabled by default, blocks once the

(3) reached across all symbols." A `reduce_only=true` order should still go through.

## 11. (Stage 2, final item) Confidence-gradient sizing: promotion is binary, allocation didn't have to be

This is the last of the seven Stage 2 items, and closes part of Scenario 34 from
`seceniors.md` (downgrading it from DANGEROUSLY MIS-HANDLED to PARTIALLY HANDLED,
not fully resolved): *"A strategy that barely clears the promotion bar gets
identical downstream capital and sizing to one that clears it comfortably. Binary
promotion collapses into binary allocation."*

### A correction to the scenario's own numbers, found while implementing

The scenario's example compared "deflated Sharpe 0.95 (bare pass)" against
"deflated Sharpe 2.0 (strong pass)." Checked directly against
`walk_forward.deflated_sharpe_ratio()`'s docstring before writing any code: *"Despite
the name this returns a probability in [0, 1], not a Sharpe ratio."* A deflated
Sharpe of 2.0 is not a real possible value — the metric is capped at 1.0. The
meaningful range for a confidence gradient is `[promotion_threshold, 1.0]` (default
`[0.95, 1.0]`), not an unbounded scale. Good thing this was checked before
implementing a formula built around the wrong range.

### The fix

Extends `vinu-portfolio`'s existing two-tilt allocation model (`regime_multiplier`,
`outcome_multiplier`, both already bounded to `±0.3` around 1.0) with a third:

- **`vinu-portfolio/vinu_portfolio/config.py`** — `PortfolioConfig` gained
  `confidence_tilt_bound: float = 0.3` (same default as the other two tilts) and
  `promotion_deflated_sharpe_threshold: float = 0.95`. The latter must track
  `vinu-research`'s own `ResearchConfig.promotion_deflated_sharpe_threshold` —
  duplicated across the service boundary the same way this session's other
  cross-service fixes were (Scenario 21's halt policy, Scenario 24's forecast
  scaling), since `vinu-portfolio` has no dependency on `vinu-research`'s config
  module.
- **`vinu-portfolio/vinu_portfolio/service.py`** — `_confidence_gradient_multiplier(
  strategy)`: for `kind == "llm_python"` strategies with a `deflated_sharpe` present,
  maps its position within `[threshold, 1.0]` linearly to `[1-bound, 1+bound]` — a
  bare pass gets `0.7x`, the metric's ceiling gets `1.3x`. Returns `1.0` (neutral,
  no penalty) for YAML strategies (which never go through this promotion bar at all)
  and for a missing `deflated_sharpe` (fail-open). Wired into `compute_daily_
  allocation()`'s existing tilt loop as a third multiplicative factor alongside the
  other two, recorded in the response as `confidence_gradient_multiplier` for
  traceability.
- **Plumbing fix required to make this possible at all**: `deflated_sharpe` wasn't
  actually reaching the `strategy` dict this multiplier reads. `_list_llm_strategies_
  in_process()` (the primary, in-process path) only returned `name`/`artifact_id`/
  `universe`; `_list_llm_strategies()`'s final transformation (which both the
  in-process and HTTP-fallback paths go through) stripped it back out even when the
  HTTP fallback's raw artifact data had it. Both fixed to propagate `deflated_sharpe`
  through — the exact same shape of bug as Scenario 20 (a real number computed
  somewhere in the codebase, silently dropped one hop before it could be used).
- **`vinu-portfolio/vinu_portfolio/game_plan.py`** — `SymbolPlan` gained a matching
  `confidence_gradient_multiplier` field for the daily-game-plan display, wired
  through in `service.py` alongside the existing `regime_multiplier`/
  `outcome_multiplier` fields there.

**What this does not touch (Scenario 34 stays PARTIALLY HANDLED, not resolved):**
- **PBO margin has no equivalent gradient.** Scenario 19's fix made PBO a hard
  threshold check at promotion (reject if PBO > 0.7) — a strategy at PBO 0.1 and one
  at PBO 0.65 (both comfortably under threshold, very different real overfitting
  risk) still get identical allocation weight. Extending the same gradient pattern to
  PBO would be the natural next step, not attempted here.
- **The promotion gate itself is still binary.** `promotion.py`'s `PromotionVerdict`
  is still eligible/not — the cliff effect at the exact threshold boundary (0.949
  rejected, 0.951 admitted) is unchanged. This fix only changes what happens to a
  strategy's weight *after* it clears that binary gate.
- **No probationary sizing for newly promoted strategies.** A strategy promoted
  five minutes ago with zero live track record gets the same confidence-gradient
  treatment as one that has been ACTIVE for months — `outcome_multiplier` (the
  separate tilt that reflects live track record) simply hasn't accumulated any
  signal yet for either, so neither gets a "new and unproven, size conservatively
  regardless of research-time metrics" penalty.

**Test coverage:** `vinu-portfolio/tests/test_service.py` gained a
`TestConfidenceGradientMultiplier` class (7 unit tests: YAML neutrality, missing-data
neutrality, at-threshold/at-ceiling/below-threshold/midpoint values, and a direct
"bare pass sizes smaller than strong pass" comparison) plus one end-to-end
integration test in `TestComputeDailyAllocation` that runs the real
`compute_daily_allocation()` path with two llm_python strategies at different
deflated-Sharpe margins and confirms their final `target_weight` actually differs.

**How to verify:** call `_confidence_gradient_multiplier({"kind": "llm_python",
"deflated_sharpe": 0.951})` vs the same with `"deflated_sharpe": 0.999` (default
threshold 0.95) — the first should return `~0.703`, the second `~1.288`, not the same
value. Running `compute_daily_allocation()` against two equally-weighted llm_python
strategies differing only in `deflated_sharpe` should produce different final
`target_weight`s.

## S3-16. Data-freshness guard: pause entries on a stalled price feed

Closes Scenario 16 from `seceniors.md`: *"Decisions Made on 30-Minute Old Data — no
freshness SLA, nothing blocks trading on stale data."*

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`, `.env`, `.env-example`
(+ tests in `test_trade_plan_orchestrator.py`).

### The problem

`orchestrator.cycle()` fetches `/stock/candles/{symbol}?interval=1d` every cycle and
uses `bars[-1]["close"]` as the live mark. Nothing ever looked at *how old* that bar
was. If the ingest pipeline stalls (provider outage, dead ingest worker, a bad
watchlist row) the newest bar simply stops advancing and every entry decision from
then on is made against a stale price, silently. `_fetch_prices` even discarded the
`bar_ts` field (`storage/models.py`: "UTC epoch seconds, bar open") that was sitting
right there in each bar dict.

### The fix

- **`_fetch_prices`** now also records `self._last_price_ts[symbol]` from
  `bars[-1]["bar_ts"]` alongside `self._last_prices[symbol]`. If a fresh price comes
  back with no usable `bar_ts`, any prior timestamp for that symbol is dropped, so the
  guard fails open rather than blocking on a lingering stale value.
- **`PRICE_MAX_AGE_HOURS`** (`VINU_LIVE_PRICE_MAX_AGE_HOURS`, default `96`, `0`
  disables) + `_price_ts_age_hours(bar_ts)` helper (returns `None` — never blocks —
  on missing/non-numeric/non-positive input, same fail-open posture as
  `_signal_age_hours`).
- **`_maybe_enter()`** — right after the signal-age check (the entries-only guard
  cluster), returns `{"action": "entry_blocked_by_stale_data", ...}` and never calls
  the broker when `data_age > PRICE_MAX_AGE_HOURS`.
- **`_evaluate_open_position()`** — the same staleness is detected but only
  **logged**, then evaluation proceeds. Exits/reduces are never gated on freshness —
  an exit on a slightly stale mark beats flying blind. Same shape as HALT
  entries-only, turbulence, and cooldown.

### Why 96h

The live cycle uses daily bars. Over a normal weekend the newest bar (Friday's) is
already ~60h old by Monday pre-market, ~84h over a 3-day weekend. 96h clears that with
buffer while still catching a feed that is genuinely days behind. **An operator
running intraday intervals must tighten `VINU_LIVE_PRICE_MAX_AGE_HOURS`** — noted in
both `.env` and the code comment. A market-calendar-aware "is this the expected most
recent session" check would be tighter but needs the calendar data source that
Scenario 2 / Stage 4 is about.

### How to verify

`TestDataFreshnessGuard` in `vinu-live/tests/test_trade_plan_orchestrator.py` (7
tests): a `_last_price_ts` 200h old + guard on → `entry_blocked_by_stale_data`,
`post_mock.call_count == 0`; no timestamp → enters (fail-open); `PRICE_MAX_AGE_HOURS=0`
→ enters; a 200h-stale feed still lets `_evaluate_open_position` fire an
`invalidation_exit`; `_fetch_prices` populates `_last_price_ts` from `bar_ts` and
clears it when a new bar lacks one.

## S3-15. Partial-fill handling: book what filled, and let reconciliation self-heal

Closes Scenario 15 from `seceniors.md`: *"Order partially filled, rest unfilled,
market moves — no fill-state tracking; risk checks continue to assume the intended
size, not the actual size."*

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`, `.env`, `.env-example`
(+ tests in `test_trade_plan_orchestrator.py`).

### The problem

`_maybe_enter` did `order_result = await self._submit_order(symbol, side, qty)` then,
on `status == "submitted"`, immediately `open_position(self._book, ..., qty, ...)` —
the **intended** qty. The `/agent/broker/order` response carries no `filled_qty`
(the fill lands async; a market order can partially fill on a thin book), so a 40-of-100
fill left the book saying 100. Every subsequent sizing / concentration / correlation /
exit / P&L calc then ran off 100 shares the account never held. The plan's note that
"`filled_qty` is already flowing through `debrief.py`" was wrong — it never reaches
`vinu-live` at all. `_reconcile_book_with_broker` already compared book vs broker every
cycle but only logged a warning.

### The fix — two backstops

**1. Confirm the fill in-cycle (`_confirm_fill`).** After a `submitted` response,
`_maybe_enter` snapshots the broker's signed position for the symbol *before* the
submit, then polls `/agent/broker/positions` up to `VINU_LIVE_FILL_CONFIRM_ATTEMPTS`
(3) times, `VINU_LIVE_FILL_CONFIRM_DELAY_SEC` (0.7s) apart. It books the **actual**
delta, not the intended one:
- delta within `VINU_LIVE_PARTIAL_FILL_TOLERANCE` (2%) of intended → full fill, book
  intended.
- smaller after all retries, but non-zero → genuine partial: book the real qty, log a
  warning, add `partial_fill: true` + `intended_qty` to the returned action.
- broker snapshot empty (untrusted / API blip) **or** symbol not visible yet (async
  lag) → fall back to intended, `False`. This never shrinks a position on a bad read;
  backstop 2 catches anything it misses. Fully disabled behaviour is unchanged when
  the broker view is unavailable (exactly today's behaviour).

**2. Reconciliation actually corrects now (`_reconcile_symbol`).** When
`VINU_LIVE_RECONCILE_AUTOCORRECT` (default `true`) is on and the broker snapshot is
**non-empty** (an empty dict can't be told apart from a failed fetch, so it's skipped),
each drifted symbol is pulled toward broker truth:
- broker flat on that symbol → `close_position` (bracket leg fired between cycles,
  etc.).
- `|broker| < |book|` → `reduce_position` down to broker (partial entry / over-exit).
- `|broker| > |book|` (same side) → `add_to_position` up to broker (partial exit left
  residual exposure) — unless the gap exceeds `VINU_LIVE_RECONCILE_MAX_RATIO` (10×),
  which is a bug not a fill → `alert_implausible_gap`, no change.
- side conflict (book long vs broker short) → `alert_side_conflict`, no change.
- broker holds a symbol the book has no position for → `alert_phantom_broker_position`,
  never auto-opened.
`_reconcile_book_with_broker`'s return dict gained a `corrections` list recording
every action taken.

### Not covered — residue cancellation

There is no `GET /agent/broker/order/{id}` or cancel-by-id route on the agent, so a
still-open residual order can't be explicitly cancelled. `vinu-live`'s orders are
`type=market, time_in_force=day`, which the exchange resolves within the session, so
the *exposure* is now tracked correctly even though the leftover working order isn't
actively killed. Adding the order-status route + residue cancel is the remaining piece.
Exits/reduces also rely on backstop 2 (one-cycle lag) rather than an in-cycle
`_confirm_fill` like entries get.

### How to verify

`TestPartialFillHandling` in `vinu-live/tests/test_trade_plan_orchestrator.py` (10
tests): full fill books intended; a 5-of-~20 broker position → books 5 with
`partial_fill: true`; empty broker snapshot / symbol-not-visible → intended (fail
open); reconciliation reduces book 100→40, closes the book when broker is flat on that
symbol (other symbols present), skips entirely on an empty snapshot, alerts (no change)
on side conflict and on a phantom broker position, and does nothing when
`RECONCILE_AUTOCORRECT` is off.

## S3-12. Runtime correlation monitor: de-risk positions that start moving together

Closes Scenario 12 from `seceniors.md`: *"Multiple positions move together
unexpectedly — no runtime correlation monitor; no auto-de-risking; DCC-GARCH
crisis-correlation is computed but has no consumer that acts on open positions."*

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`, `.env`, `.env-example`
(+ tests in `test_trade_plan_orchestrator.py`).

### The problem

`_compute_covariance()` already builds a DCC/shrinkage covariance
(`vinu_tools.compute.risk.covariance.dynamic_covariance`) over the recent price
series of the open symbols — but the only consumer was the breaker's aggregate
portfolio-VaR check (`_check_aggregate_var`: `wᵀ Σ w`). Nothing looked at the
**pairwise** correlation between the positions actually held and cut exposure when two
of them became a single concentrated bet. Scenario 12 is rated a portfolio-blowup gap.

### The fix

New `_check_runtime_correlation(prices)`, called once per cycle right after
reconciliation:

1. `_compute_covariance(open symbols)` → `correlation_from_covariance()` (same
   `vinu_tools` module — no new math).
2. Per symbol, net **signed** exposure (long +1 / short −1, summed) and gross market
   value.
3. For each pair, `comovement = corr · sign(exposure_a) · sign(exposure_b)` — this is
   the co-movement *in the direction the book is actually exposed*. Two correlated
   longs → high positive comovement (concentrated). A correlated long+short → negative
   (that's a hedge, left alone). A symbol whose own positions net flat → skipped.
4. `comovement ≥ VINU_LIVE_RUNTIME_CORR_THRESHOLD` (0.85) flags the pair. The **larger**
   position of the pair (by market value) is `reduce_only`-trimmed by
   `VINU_LIVE_RUNTIME_CORR_REDUCE_PCT` (25%).
5. `self._last_corr_reduce[symbol]` (monotonic time) enforces a per-symbol
   `VINU_LIVE_RUNTIME_CORR_COOLDOWN_SEC` (1h) — it trims a name once, not every 90s.
6. `reduce_only=True` means it routes through the same OrderGuard exemption as every
   other exit/reduce (survives a kill-switch halt, can only ever cut risk).

`cycle()`'s result dict gains `correlation_monitor` with the flagged pairs and any
reductions.

**Default ON** — like the data-freshness guard and reconciliation self-heal, and
unlike the CVaR hard-block. The action is bounded (25%, once/hour/symbol),
strictly risk-reducing, and only fires on a genuinely dangerous condition.
`VINU_LIVE_RUNTIME_CORR_ENABLED=false` disables it.

### How to verify

`TestRuntimeCorrelationMonitor` in `vinu-live/tests/test_trade_plan_orchestrator.py`
(7 tests): two 0.95-correlated longs → the larger (by MV) is trimmed 25%, the other
untouched; a correlated long+short pair is **not** flagged (hedge); corr 0.5 → no
action; disabled flag / <2 symbols / covariance `None` → clean no-op; a second cycle
inside the cooldown still flags the pair but does not trim again.

## S3-3-5. Conflicting-signal detection: refuse to open a symbol another live plan wants short

Closes Scenarios 3 and 5 from `seceniors.md`: two ACTIVE strategies can name the same
symbol with opposing signals, and the system would hold a long that another promoted
strategy currently says to be short — "diversified" on paper, one contested bet in
reality.

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py` (+ tests).

### The problem

`_fetch_active_trade_plans()` returns *all* ACTIVE `trade_plan` artifacts; `cycle()`
loops them and calls `_maybe_enter` per plan. Nothing checked whether two plans for
the same symbol agreed — whichever the loop reached first opened the position and the
opposing plan was silently ignored (it then just evaluated against the existing
position via `_evaluate_open_position`). A 1D sweep long + a 1H sweep short on the same
ticker was structurally possible and invisible as a conflict.

### The fix

- `_opposing_active_signal(plan, symbol, direction, all_plans)` — module helper,
  returns a reason string if any *other* ACTIVE plan for `symbol` has the opposite
  `direction`, else `None`.
- `_maybe_enter(...)` gained `all_plans: list | None = None`. When it's provided and
  `VINU_LIVE_SIGNAL_CONFLICT_POLICY == "block"` (the default), an opposing signal
  returns `{"action": "entry_blocked_by_signal_conflict", "reason": ...}` and no order
  is placed. `policy=ignore` restores the old first-plan-wins behaviour.
- Both `_maybe_enter` call sites (`cycle()` and the shock-trigger `_evaluate_plan`)
  pass the plan list they already have; the arg defaults to `None` so any other caller
  is unaffected.

**Blocks rather than nets.** Netting two opposing signals into a small residual
position trades size nobody sized deliberately; refusing to open into a contested
symbol is the conservative call and leaves the conflict visible in the action log for
a human / the allocator to resolve.

### How to verify

`TestSignalConflictDetection` (5 tests): opposing ACTIVE plan → `entry_blocked_by_
signal_conflict`, no order; agreeing plans enter; an opposing plan on a *different*
symbol is not a conflict; omitting `all_plans` keeps old behaviour; `policy=ignore`
enters anyway.

## S4-13. Liquidity / spread gate (`#13`)

Closes the Stage 4 half of the microstructure gap: every entry so far was priced

right now at a sane cost**. A wide bid/ask (thin pre-market, a halt-then-reopen,

### The fetch → store → consume wiring

- **Fetch** — `quote.py` `AlpacaQuoteProvider.get_quote(symbol)` calls Alpaca

## S4-14A. Broker-outage pause (`#14` Half A)

Closes the entry-side half of Scenario 14 (`seceniors.md`): if the broker API
goes dark mid-session, nothing stopped `cycle()` from firing entry after entry
into a dead endpoint — each one erroring individually with no system-level
"the broker is down, stop opening" response. **No new data source** — reuses the
existing `/agent/broker/account` probe.

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`; `.env` /
`.env-example` (+ tests).

### The wiring

- **`__init__`** — `self._broker_ok_at: float = 0.0` (monotonic time of last
  healthy probe; `0.0` = never confirmed since start) and
  `self._broker_degraded: bool = False`.
- **Module constant** — `BROKER_STALE_SEC = VINU_LIVE_BROKER_STALE_SEC`
  (**default 180s**, `0` disables the whole guard). 180s spans two 90s cycles
  so a single transient blip does not pause trading.
- **`_check_broker_health()`** — new method, called once per `cycle()`
  **before the plan loop** (so `_maybe_enter` sees this cycle's state):
  - healthy 200 ⇒ stamp `_broker_ok_at = monotonic()`, clear
    `_broker_degraded` (logs "recovered" on the clearing edge). A
    reachable-but-unconfigured broker still counts as healthy — that is a
    deployment state, not an outage.
  - non-200 / transport error ⇒ if `_broker_ok_at == 0.0` (never confirmed)
    **or** `monotonic() - _broker_ok_at > BROKER_STALE_SEC` ⇒ set
    `_broker_degraded = True`. Otherwise (a blip inside the grace window)
    leave it False and return `within_grace: True`.
  - returns a status dict → `result["broker_health"]`.
- **`_maybe_enter`** — right after the direction check (before every other
  guard): `if BROKER_STALE_SEC > 0 and self._broker_degraded:` ⇒ return
  `{"action": "entry_blocked_by_broker_outage", ...}`.
- **Exits / reduces never gated** — `_evaluate_open_position` has no branch on
  `_broker_degraded` (same entries-only shape as HALT / turbulence / cooldown /
  spread / data-freshness).

## S4-33. Emergency flatten (`#33` part 1 — the panic switch)

Closes the *response* half of Scenario 33: the system had shock **detection**
(DCC-GARCH crisis correlation, shock clustering) but no shock **response** beyond
the automatic −20% kill switch. There was no single deliberate "get me out of
everything, now" action.

**Scope:** `#33` part 1 (manual flatten) only. Part 2 — an automatic
out-of-distribution detector that *fires* the flatten — is deferred
(needs feature-distribution monitoring; post-launch).

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`,
`vinu-live/vinu_live/server/app.py` (+ tests). No `.env`, no Compose.

### What it does

- **`orchestrator.emergency_flatten(reason)`** — two steps:
  1. `POST {agent}/agent/broker/halt` — sets the **existing** filesystem kill
     switch (`vinu-agent/broker/kill_switch.py`), which `OrderGuard` already
     enforces on *every* order from *every* service (cross-process, survives a
     restart). `reduce_only` exits keep passing (the Stage 1 exemption).
  2. `list_open_positions(book)` → for each, submit a `reduce_only` market close
     (`_submit_order`, opposite side, full qty) and `close_position()` on
     confirm. A close that doesn't confirm leaves the position in the book —
     `_reconcile_book_with_broker` pulls it straight next cycle. Nothing is
     hidden: `positions_failed` is returned.
  - Returns `{status: ok|partial, halted, positions_closed[], positions_failed[],
    count_closed, count_failed}`.
- **`orchestrator.emergency_resume(reason)`** — `POST {agent}/agent/broker/resume`
  + clears the local breaker. Does **not** reopen anything. Deliberately
  separate so a flatten never silently un-does itself.
- **`orchestrator.emergency_status()`** — `{halted, local_breaker_halted,
  open_positions}`.
- **`_is_trading_halted()`** + `self._trading_halted` — once per `cycle()` (right
  after the broker-health probe) the orchestrator mirrors
  `GET /agent/broker/status`. `_maybe_enter` returns
  `entry_blocked_by_emergency_halt` while set — fast, explicit local shortcut;
  the authoritative gate is still OrderGuard's kill-switch check. Fail-safe on
  an unreachable agent is *not halted* (orders can't be placed anyway; the
  broker-outage guard covers that; a real halt file is re-read next cycle).

### Routes (vinu-live, all under `/live`, auth-gated)

- `POST /live/trade-plan/emergency-flatten` `{reason?}` → the flatten result
- `POST /live/trade-plan/emergency-resume` `{reason?}` → lift the halt
- `GET  /live/trade-plan/emergency-status` → current state

## S4-33b. Out-of-distribution auto-detector (`#33` part 2 — the automatic trigger)

Completes Scenario 33: `#33` part 1 gave a *manual* flatten; this is the
detector that decides "this is the event" and pulls it. **Ships DORMANT** — an
auto-flatten that false-positives liquidates the whole book, so it is `off` by
default and activated in graduated steps, each earned by observing the one below
it in paper.

**Files:** `vinu-live/vinu_live/trade_plan/orchestrator.py`; `.env` /
`.env-example` (+ 7 tests).

### The detector

`orchestrator._check_ood(prices)`, run once per `cycle()` **after** the
correlation monitor (so it sees the post-trim book). Three fail-open signals
scored over the **open positions only**:

| Signal | Fires when | Knob (default) |
|---|---|---|
| `crisis_correlation` | mean \|pairwise corr\| of the open book ≥ threshold (DCC/shrinkage cov → `correlation_from_covariance`, reused from `#12`) | `VINU_LIVE_OOD_CORR` (0.95) |
| `vol_explosion` | mean 14-bar realized vol across held names ≥ threshold | `VINU_LIVE_OOD_VOL` (0.08 daily ≈ ~127% annualised) |
| `gap_move` | any held name's latest 1-bar move ≥ threshold | `VINU_LIVE_OOD_MOVE` (0.10) |

Triggers only when **≥ `VINU_LIVE_OOD_MIN_SIGNALS` (2)** fire in the same cycle —
no single noisy input can act. Any signal whose data is missing simply doesn't
contribute (fail-open).

### Graduated activation — `VINU_LIVE_OOD_DETECTOR`

| Value | On trigger |
|---|---|
| `off` *(default)* | `_check_ood` returns `{"checked": false, "reason": "disabled"}` — not even run |
| `alert` | log + full detail in `result["ood_detector"]`, **no action** — run this for weeks in paper, see how often it *would* have fired |
| `halt` | `POST /agent/broker/halt` — block new entries, leave positions open |
| `flatten` | `emergency_flatten(reason="auto-OOD [...]")` |

**Latched** (`self._ood_acted`): after it acts once this process lifetime it
will not act again until `emergency_resume()` or a restart — an auto-flatten is
a one-shot, not a loop. `alert` mode is not latched (it just keeps reporting).

### How to verify

`vinu-live/tests/test_trade_plan_orchestrator.py` new `TestOODDetector` (+7):
disabled by default; `alert` detects (`triggered:true`) but `acted:false` and
never calls `emergency_flatten`; `flatten` awaits `emergency_flatten` once and
sets `_ood_acted`; `halt` trips `_trading_halted` and leaves positions open;
one signal alone (high corr, calm returns) → `triggered:false`; no open
positions → no-op; a pre-set `_ood_acted` latch → `triggered:true` but no repeat
action.

```
vinu-live: pytest tests/ -q  → 247 passed (7 new), 6 failed, 3 errors
           (same pre-existing baseline.)
```

### Activation playbook (for the operator)

1. Ship `off`. 2. During the paper soak, set `alert` and watch how many cycles
   report `triggered:true` — tune `OOD_CORR` / `OOD_VOL` / `OOD_MOVE` /
   `OOD_MIN_SIGNALS` until false positives are rare. 3. Move to `halt`. 4. Only
   once `halt` has behaved correctly through real volatility, move to `flatten`.

### Not done

- No VIX / external-vol input — signals are all derived from the book's own
  price history (no market-wide feed wired).
- No auto-*resume* — lifting an auto-halt/flatten is always a deliberate
  `emergency-resume` call.

## S-FIX. Book↔broker consistency — 4 bugs found by a live end-to-end trace (2026-09-10)

Ran a real trade start-to-finish on the paper stack (injected an ACTIVE
`trade_plan`, watched entry → fill → hold → exit). The core path (guards,
sizing, fill, halt) was sound; four defects in **book↔broker consistency under
concurrency + settlement lag** surfaced. All four fixed.

**Files:** new `vinu-live/vinu_live/book/lock.py`;
`vinu-live/vinu_live/trade_plan/orchestrator.py`; `.env` / `.env-example`
(+ `TestReconcileRobustness`, 11 tests).

### #1 — reconcile races a fresh fill's broker-propagation lag

`_reconcile_book_with_broker` runs ms after an entry fills; Alpaca's `/positions`
hadn't caught up (returned ~1 share of a 5.74-share fill) → reconcile **trimmed
the correct book position to the stale broker view**. Next cycle it corrected
back up — endless oscillation.

**Fix:** `self._recently_traded[symbol] = monotonic()` stamped by every
order-placing path (`_maybe_enter`, `_apply_invalidation`, `_apply_contingency`
reduce, `_check_runtime_correlation` trim, `emergency_flatten`).
`_reconcile_book_with_broker` **defers** auto-correct for a symbol traded within
`VINU_LIVE_RECONCILE_SETTLE_SEC` (default 12s) — logs `deferred`, corrects it
normally next cycle. Live-verified: entry cycle now reports
`"deferred": ["AAPL"]`, book untouched.

### #2 — two orchestrators, one book, no lock

The `entrypoint.sh` background worker *and* the throwaway orchestrator each
`/live/trade-plan/*` route builds both open their own SQLite connection to the
same book. Concurrent `_reconcile_book_with_broker` → both read the same stale
qty, both `add_to_position` the same delta → book at ~2x broker.

**Fix:** new `book_lock()` — `fcntl.flock` / `msvcrt.locking` cross-process lock
(same pattern as `vinu-agent`'s `kill_switch_lock()`), lock file at
`<book db>.lock`. Wrapped around every book read-decide-write: the reconcile
body (book re-read *inside* the lock, after the network fetch), and each
`open_position` / `close_position` / `reduce_position` call in the entry / exit /
flatten / correlation-trim paths. Held only over local work, never across an
`await`. `VINU_LIVE_BOOK_LOCK_PATH` overrides; `":memory:"` books disable it.

### #3 — `emergency_flatten` over-asked vs the real broker holding

It submitted a reduce_only close for the **book qty** (which #1/#2 had briefly
left at `6.0`) while the account held `5.7388` → **Alpaca 403** (can't
reduce_only more than held). The position stayed open.

### #4 — exit paths sold into a flat / opposite account

After the account was externally flat but the book still showed `+6`,
`_apply_invalidation` sent `SELL 6` → **opened a 6-share short**. `reduce_only`
was set but Alpaca paper treats sell-from-zero as a new short.

**Fix for #3 + #4:** new `_broker_close_plan(symbol, book_side, book_qty)` —
reads the live broker position and returns `(qty_to_send, side, note)`:
`"ok"` → close `min(book_qty, |broker_qty|)` on the side that flattens the
broker; `"broker_flat"` → send **no order**, just close the stale book position;
`"side_conflict"` → send no order, alert; `"no_broker_view"` → fall back to book
qty. Used by `emergency_flatten`, `_apply_invalidation`, and the
`_apply_contingency` reduce. New action strings: `invalidation_exit_book_only`,
`reduce_book_only`, `exit_blocked_side_conflict`, `reduce_blocked_side_conflict`.
Live-verified: `emergency_flatten` closed exactly `5.7556` (broker qty), Alpaca
went to `404 position does not exist` (flat, no short).
