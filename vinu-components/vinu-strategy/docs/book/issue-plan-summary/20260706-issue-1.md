# vinu-strategy: Version 1 Issues

Date: 2026-07-06

---

## Issue 1.1: `select_threshold` ignores the `on`/`field` parameter

**File:** `vinu_strategy/engine/selection.py:15-18`

**Problem:** The `field` parameter is read from YAML config (e.g., `on: MOM_20`) but never used for filtering. The function always compares against the aggregated signal value instead of the specified feature field.

**Impact:** Strategies using `selection.method: threshold` with a specific field (like `news_aware_momentum` with `on: MOM_20`) do not filter correctly.

---

## Issue 1.2: Signal expressions in YAML not evaluated

**Files:** `vinu_strategy/engine/allocation.py`, `ma_crossover.yaml`, `rsi_mean_reversion.yaml`

**Problem:** YAML files define custom signal expressions like `"SMA_9 / SMA_21 - 1"` and `"max(0, (30 - RSI_14) / 30) - max(0, (RSI_14 - 70) / 30)"` in the `pipeline.allocation.signal` field. The `allocate_signal_scaled` function ignores these and uses `abs(signals.get(sym, 0.0))` instead.

**Impact:** MA crossover and RSI mean reversion strategies produce incorrect weights. Signal expressions are dead code.

---

## Issue 1.3: Correlation flattening has redundant confusing code

**File:** `vinu_strategy/service.py:73-76`

**Problem:** A nested `if impact in ... and granger in ...` block pre-extracts keys from `impact` and `correlation` dicts into `ctx`, but `_flatten_correlation_context()` already handles all dict values. The code is redundant and misleading — it looks like drawdown data is never merged (though it actually is, by the flatten function).

**Impact:** Code maintainability. No runtime bug, but confusing to readers.

---

## Issue 1.4: Risk params have hardcoded defaults

**File:** `vinu_strategy/engine/pipeline.py:46-48`

**Problem:** `risk_params.setdefault("max_weight", ..., 0.25)` and `... "cash_floor", ..., 0.10)` use hardcoded values instead of relying on the config. If `VinuStrategyConfig` defaults are changed, the pipeline ignores them.

**Impact:** Configuration inconsistency. YAML params override config correctly, but the hardcoded fallback is dead code.

---

## Issue 1.5: Operator parsing in rules is fragile

**File:** `vinu_strategy/models/rules.py:16-21`

**Problem:** The operator detection iterates a tuple of operator names and checks `if possible_op in d`. If a dict coincidentally has two operator keys, only the first one in iteration order is picked.

**Impact:** Edge case — unlikely in practice but fragile.

---

## Issue 1.6: Sequential API fetches for features and correlation

**File:** `vinu_strategy/service.py`

**Problem:** Feature and correlation data are fetched one symbol at a time in a `for sym in universe` loop. For universes of 50–500 symbols, this creates sequential HTTP requests that could take minutes.

**Impact:** Performance. No concurrency for API calls. Also, `httpx.Client` is not thread-safe for shared use.
