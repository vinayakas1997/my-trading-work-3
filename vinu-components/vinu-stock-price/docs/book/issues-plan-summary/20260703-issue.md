# vinu-stock-price Code Quality & Performance Audit

**Date:** 2026-07-03  
**Scope:** `vinu_stock/` (all Python source), `providers/`, `storage/`, `query/`, `catalog/`, `live/`, `backfill/`, `server/`

## Performance Issues (High Impact)

### 1. `write_bars` / `append_bars` rewrites entire file on every append

**File:** `vinu_stock/storage/parquet.py:54-62`

Every call to `append_bars` (which runs every live ingest cycle ~60s) reads the **entire** existing parquet file into memory, merges a handful of new bars, deduplicates, and writes everything back from scratch.

```python
def write_bars(path, bars, *, merge=True):
    combined = list(bars)
    if merge and path.is_file():
        combined = _read_existing(path) + combined   # reads full file
    combined = _dedupe_bars(combined)
    pq.write_table(_bars_to_table(combined), path, compression="zstd")
```

- **Impact:** O(n) memory + O(n) I/O per append. With 6+ months of 1m data (~175k rows), this becomes very expensive every 60 seconds.
- **Fix:** Use DuckDB `COPY` or `INSERT` to append new row groups, or write to separate daily files and merge periodically.

---

### 2. No parquet partition pruning in DuckDB queries

**File:** `vinu_stock/query/engine.py:40-46`

DuckDB is given glob patterns for `archive/*.parquet` + `live/*.parquet`. For a symbol with 15 years of data, it opens and scans all 15+ files, then filters via SQL `WHERE bar_ts >= ? AND bar_ts <= ?`.

```python
placeholders = ", ".join(f"'{p}'" for p in patterns)
sql = f"""
    SELECT ... FROM read_parquet([{placeholders}], union_by_name=true)
    WHERE symbol = ? AND bar_ts >= ? ...
"""
```

- **Impact:** Every query scans every parquet file regardless of time range.
- **Fix:** Dynamically construct globs based on `from_ts`/`to_ts` so only relevant year files are read. Use DuckDB's `hive_partitioning=true` or explicit file list.

---

### 3. `aggregate_bars` sorts already-sorted data twice

**File:** `vinu_stock/query/aggregate.py:33,54`

DuckDB already returns rows in `ORDER BY bar_ts ASC`, but `aggregate_bars` sorts again via `sorted(rows, key=lambda r: r["bar_ts"])`. Then for higher intervals, it sorts the output buckets again via `sorted(buckets)`.

```python
for row in sorted(rows, key=lambda r: r["bar_ts"]):  # sort #1
    ...
return [buckets[k] for k in sorted(buckets)]          # sort #2
```

- **Impact:** Two unnecessary O(n log n) sorts per query. For 5000 rows with 1m interval, it sorts just to return the same ordering.
- **Fix:** Remove the redundant sort if DuckDB already orders; use `dict(sorted(...))` in one pass or trust input order.

---

### 4. `_rolling_std` allocates a new filtered list per window

**File:** `vinu_stock/query/indicators.py:146-155`

For each position `i`, it builds a filtered list comprehension over the window:

```python
def _rolling_std(values, period):
    for i in range(period, len(values)):
        window = [v for v in values[i - period + 1 : i + 1] if v is not None]
        ...
```

- **Impact:** O(n × period) memory allocations. For `period=20` and `n=5000`, this creates ~100k intermediate lists.
- **Fix:** Use a sliding window with a deque that tracks only non-None values.

---

### 5. Indicators recomputed on every HTTP request

**File:** `vinu_stock/query/engine.py:66-69`

SMA(5/10/20/50), RSI(14), MACD, daily_return, volatility_20d are computed from scratch per `/candles` request. No caching or persistence of computed values.

```python
records = aggregate_bars(records, interval)
if adjusted:
    records = apply_adjusted_prices(records)
if indicators:
    records = apply_indicators(records, indicators)
```

- **Impact:** Every front-end chart refresh triggers full indicator recomputation (multiple passes through 5000+ rows).
- **Fix:** Add a DuckDB-based or Redis cache keyed on `(symbol, interval, range, indicator_set)`. Or push indicator computation into DuckDB SQL.

### 6. `data_root` property calls SQLite on every access

**File:** `vinu_stock/service.py:51-53`

```python
@property
def data_root(self) -> Path:
    settings = self._backend.get_settings()  # SQLite round-trip
    return Path(settings.data_root)
```

- **Impact:** Every call to `run_backfill`, `run_live_cycle`, `get_candles` triggers a SQLite query.
- **Fix:** Cache `data_root` on init (e.g., `self._data_root = Path(settings.data_root)`), or invalidate only on settings patch.

### 7. `_discover_first_year` calls provider APIs even for known symbols

`_discover_first_year` always probes provider APIs even if the symbol already has `first_bar_ts` in the catalog (from a previous backfill).

### 9. `update_bar_range` → `upsert_symbol` double-queries SQLite

**File:** `vinu_stock/catalog/store.py:151-177`

```python
def update_bar_range(self, symbol, bars, *, provider, live_file=None):
    entry = self.get_symbol(symbol)        # SQL query #1
    ...
    self.upsert_symbol(...)                # calls get_symbol() again (line 94)

def upsert_symbol(...):
    existing = self.get_symbol(sym)         # SQL query #2 (redundant)
```

- **Impact:** 2x SQL queries per symbol update.
- **Fix:** Add an `upsert_symbol` overload that accepts existing entry to skip re-fetch, or use `INSERT ... ON CONFLICT DO UPDATE`.

### 10. Live ingest: N SQL queries for N symbols

## Code Quality & Inconsistencies

### 11. `_symbol_to_yahoo` is dead / misleading code

**File:** `vinu_stock/providers/yahoo.py:18-23`

```python
def _symbol_to_yahoo(symbol: str) -> str:
    s = symbol.strip().upper()
    if "." in s or "/" in s or "-" in s:
        return s
    return f"{s}"  # identical to the strip+upper above
```

- **Issue:** Returns the exact same string regardless of the condition. No transformation.
- **Fix:** Remove or implement actual Yahoo-specific symbol mapping.

---

### 12. `retry_on_transient` decorator defined but never used directly

**File:** `vinu_stock/providers/retry.py:17-52`

The `retry_on_transient` decorator is only used internally by `http_get_with_retry`. Alpaca and Polygon providers call `requests.get()` directly with zero retry logic.

- **Issue:** Duplicate code; only Yahoo benefits from retries.
- **Fix:** Apply `http_get_with_retry` to Alpaca and Polygon, or use a shared session with retry adapter.

---

### 13. Inconsistent HTTP retry across providers

| Provider | File | Retry Mechanism |
|---|---|---|
| Yahoo | `yahoo.py:50` | `http_get_with_retry` (3 attempts, backoff) |
| Alpaca | `alpaca.py:60` | Raw `requests.get()`, no retry |
| Polygon | `polygon.py:48` | Raw `requests.get()`, no retry |

- **Issue:** Yahoo gets retry protection; Alpaca/Polygon fail immediately on transient errors.
- **Fix:** Standardize all providers to use `http_get_with_retry`.

---

### 14. API key exposed in URL query string

**File:** `vinu_stock/providers/polygon.py:44`

```python
params = {"adjusted": "true", "sort": "asc", "limit": 50000, "apiKey": self._config.polygon_api_key}
```

- **Issue:** The Polygon API key appears in the URL query string, which is logged by HTTP proxies, load balancers, and server access logs.
- **Fix:** Polygon.io supports API key via `Authorization` header: `{"Authorization": "Bearer " + key}`.

---

### 15. Race condition in `upsert_symbol` (SELECT-then-INSERT)

**File:** `vinu_stock/catalog/store.py:94-117`

```python
existing = self.get_symbol(sym)   # SELECT
if existing is None:
    self._conn.execute("INSERT ...")   # INSERT
else:
    self._conn.execute("UPDATE ...")
```

- **Issue:** Two concurrent calls can both get `None` from `get_symbol` and both try to INSERT, causing an `IntegrityError`.
- **Fix:** Use `INSERT INTO ... ON CONFLICT DO UPDATE` (SQLite 3.24+).

---

### 16. Schema migration not thread/process-safe

**File:** `vinu_stock/catalog/store.py:53-63`

```python
def _migrate_schema(self):
    cols = {row[1] for row in self._conn.execute("PRAGMA table_info(symbol_catalog)")}
    for name, typedef in migrations:
        if name not in cols:
            self._conn.execute(f"ALTER TABLE symbol_catalog ADD COLUMN {name} {typedef}")
```

- **Issue:** Two processes starting simultaneously can both detect a missing column and both issue `ALTER TABLE ADD COLUMN`. One will fail.
- **Fix:** Use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (SQLite 3.35+) or catch/suppress the error.

### 17. Backfill blocks the HTTP server

**File:** `vinu_stock/server/routes_config.py:72-82`

```python
@router.post("/backfill/trigger")
def trigger_backfill():
    result = get_service().run_backfill()  # synchronous, blocking
```

- **Issue:** A backfill that takes hours will block the entire FastAPI server from handling any other request.
- **Fix:** Run in a background thread/process and return a job ID. Poll for completion.

### 23. Exception type abuse in retry mechanism

**File:** `vinu_stock/providers/retry.py:67-68`

```python
if resp.status_code in (429, 500, 502, 503, 504):
    raise requests.ConnectionError(f"HTTP {resp.status_code}")
```

- **Issue:** HTTP 429 (Rate Limited) and 5xx errors are not `ConnectionError` — they are protocol-level errors. This abuses exception types for control flow.
- **Fix:** Define a custom `TransientProviderError` or use `requests.HTTPError`.

### 24. `_discover_first_year` duplicates fallback logic

**File:** `vinu_stock/backfill/orchestrator.py:43-54`

The function manually iterates backfill providers, then separately tries Yahoo:

```python
for provider in registry.for_role("backfill"):
    ...
# Yahoo fallback
yahoo = registry.get("yahoo")
if yahoo:
    ...
```

- **Issue:** The `ProviderRegistry` already has `fetch_bars_with_fallback` with fallback ordering. `_discover_first_year` reimplements what the registry could handle.
- **Fix:** Use `registry.fetch_bars_with_fallback(sym, start_ts, end_ts, role="backfill")` inside `_discover_first_year` and extract earliest from result.

### 25. `interval` parameter in Polygon `fetch_bars` is accepted but ignored

**File:** `vinu_stock/providers/polygon.py:33`

```python

```

The `interval` parameter is accepted but the URL always requests `/range/1/minute/...` regardless of value.
