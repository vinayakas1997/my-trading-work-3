## Fixes Applied

### P0 — Blocking request / silent failure risk

| Issue | Description | Change |
|-------|-------------|--------|
| C1 | `POST /backfill/trigger` ran the full multi-chunk fetch loop (`run_backfill_single`/`run_backfill_all`) synchronously inside the request handler, blocking until the entire backfill finished. Any client/proxy timeout during a long backfill silently killed the connection with no way to check outcome, and there was no guard against two overlapping triggers racing on `backfilled_up_to_ts`. | Ported the job-tracking pattern already used by `vinu-stock-price` (`server/routes_config.py:103-157`): the route now spawns a daemon thread, returns a `job_id` immediately (`{"ok": true, "summary": {"job_id": ..., "status": "running"}}`), records progress/result/error in an in-memory `_background_jobs` dict guarded by `_jobs_lock`, and rejects a second trigger with `409` while one is running (`_backfill_lock`, non-blocking acquire). Added `GET /backfill/job/{job_id}` for polling. Updated `web/src/App.jsx` (`triggerBackfillSingle`, `triggerBackfillAll`) to read the returned `job_id` and poll the new endpoint every 2s instead of reading `results` off the trigger response directly. |

## Notes / Verified preconditions

- `SqliteBackend` (`vinu_news/storage/sqlite_backend.py:36-62`) already uses thread-local connections, so writes from the background thread don't collide with the request thread's connection — no storage-layer change needed.
- `vinu-news-serve` runs uvicorn with no `--workers` (`cli.py:153`), i.e. single process — the in-memory `_background_jobs` dict is safe (no risk of a job created on one worker being invisible to a status poll on another).
- CLI paths (`cli.py:100,179-183`) call `NewsService.run_backfill_single`/`run_backfill_all` directly, not through the HTTP route — unaffected by this change.
