# FinceptTerminal

https://github.com/Fincept-Corporation/FinceptTerminal · 31.3K stars · First released 2024-08-29 · Last updated 2026-09-08

**Second-highest-value repo of the 13, specifically for the scan-mechanics half of `vinu-screener`** — the `fincept-qt/src/algo_engine/` subsystem (`ConditionEvaluator`, `ScanMonitor`, `RealtimeScanRunner`, `AlgoScanner`) is the cleanest condition-schema and scan-execution reference of anything audited. Note: this was wrongly dismissed as "just UI screen-routing" in an earlier shallow filename-only grep — a proper content read found the real scanner buried under `algo_engine/`.

## Advanced Features

- **Nested-boolean condition JSON schema, a strict superset of a flat rule list** — a condition node is either a comparison leaf `{indicator, params, field, offset, operator, compare_mode, value|compare_indicator, compare_params, compare_field, compare_offset}` or a nested group `{children:[...], logic: AND|OR, negate: bool}`, letting rules express `(A AND B) OR C`. Backward compatible: a flat array of leaves (legacy schema) still evaluates unchanged. `ConditionEvaluator.h` (comment lines 12-28), `.cpp` `parse_condition`/`evaluate_group` (lines 188-231, AND/OR short-circuit at 218-226).
- **Every operand carries an explicit `offset` (bars-ago)**, resolved by recomputing the indicator on a truncated candle window (`operand_value`, lines 81-110), so "RSI 3 bars ago > 70" is expressible without a separate lookback DSL.
- **Non-finite-value poisoning bug class explicitly guarded against** — a code comment (`ConditionEvaluator.cpp` lines 16-22) documents that `std::isnan(inf)` is false, so an `inf` indicator value (e.g. a % change against a zero reference price) previously satisfied `inf > threshold` and fired false live entries; fixed via a single `cond_non_finite()` choke point (`!std::isfinite(v)`) applied to every operand before any comparison, crossing, or level-touch check. Exactly the kind of correctness bug a rule-based scanner over ~8000 symbols with heterogeneous price histories (delisted, halted, zero-volume symbols) will hit in practice.
- **A float-tolerant "level touch" operator for polled (non-tick) live data** — the `==` operator fires either when `|lhs-rhs| <= tol` (relative tolerance, `tol = |rhs|*1e-7`, floored at `1e-9`) OR when the sign of `(lhs-rhs)` flipped between the previous and current sample (price crossed through the level between polls). Directly solves "how do I detect a price level cross with discrete polling."
- **`crosses_above`/`crosses_below`/`rising`/`falling` all read one extra bar back automatically** (`op_needs_prev`) — the evaluator itself decides which operators need `t-1` state, callers don't have to know.
- **Two parallel scan execution modes sharing the same condition evaluator** — `ScanMonitor` (poll mode) runs on a timer (`interval_sec`, floored at 30s "rate limits") re-fetching candles and re-evaluating `ConditionEvaluator::evaluate_group` per symbol; `RealtimeScanRunner` instead subscribes the whole universe to a live quote feed and does a **coalesced sweep** every `sweep_ms` (default 500ms, floored at 100ms) evaluating only symbols that "priced since the last sweep" (`dirty` flag) — avoids re-evaluating the whole universe on every tick.
- **Edge-gated, per-symbol cooldown firing** — both modes share the same mechanism: an `armed` boolean per symbol (fire only on false→true transition of the condition, not every bar it stays true) combined with a `cooldown_min` minimum gap between fires.
- **Auto-computed minimum lookback from the condition tree** — `RealtimeScanRunner::required_bars()` recursively walks the condition JSON and computes `max(indicator period, compare period) + max(offset, compare_offset) + 2` (the `+2` covers the one-bar-back needed for crossing operators), floored at 2 — determines how much warm-up history/buffer size each symbol's candle aggregator needs before it's eligible to evaluate (`warmed` flag).
- **One-shot vs persistent watch semantics baked into the poll-mode dispatch** — a poll-mode watch that fires is **removed from the active watch table** after firing once ("one-shot" semantics), while the fired event stays in a separate `scan_watch_events` history table for audit; realtime-mode watches instead keep running after a match — deliberately different retention policy per mode.
- **Alert dispatch as a fan-out gated by a JSON `actions` bag on the watch itself** — `actions.toast` (default true) → local toast notification, `actions.providers` (default false) → external `NotificationService` (email/webhook/etc.), always writes a `touch_fired` timestamp + a persisted audit row + emits a Qt signal for any UI listener — fully decoupled from evaluation.
- **`ScanWatch` persisted schema** — `conditions` (QJsonArray), `logic`, `symbols`/`universe` (supports named universes like `NIFTY50`, `NSE_EQ`, `BSE_EQ` resolved live, or a custom symbol list), `timeframe`, `lookback_days`, `data_source`, `mode` (`poll`|`realtime`), `interval_sec`, `cooldown_min`, `actions`, `active`, `status`, `last_eval_at`, `last_fired_at` — essentially the exact data model a `vinu-screener` rule row needs.
- **Human-approval-gated live order path exists as a fully separate concern from the scanner** — a separate `DeploymentRunner` handles `on_order_queued_for_approval`/`on_approval_resolved`; the scanner itself is explicitly commented "there is NO position/order machinery here."

## Why It's Trusted / Mature

The scanner subsystem is trustworthy specifically because of its hard separation of concerns: `ConditionEvaluator` is pure/stateless (no members, just static functions over an explicit candle window), the two runners (poll vs realtime) share that one evaluator but differ only in data-feed strategy, and neither touches order/position machinery at all — it's explicitly commented as alert-only. That means the scanner can be trusted not to accidentally place a trade, and its correctness bugs (like the non-finite-value fix) are narrowly scoped to the evaluator, not spread through order logic where a bug would be far more dangerous. The auto-derived `required_bars()` warm-up calculation also protects against an entire class of bugs (evaluating on insufficient history) that a naive scanner would hit constantly at 8000-symbol scale, and the fact that it's an actively-developed 31K-star project (despite a June 2026 maintenance-notice slowdown) means this design has been exercised against real, messy market data, not just a clean test fixture.

## vs Vinu — Gap & Adoptable Logic

**Gap:** This is squarely the gap `vinu-screener` is trying to fill — Vina currently has nothing described as a rule-based scanner at all. What FinceptTerminal has that Vina doesn't yet: (a) a formalized nested-boolean condition JSON schema with offset/compare-indicator support; (b) an explicit cooldown + edge-gate firing model to avoid alert spam; (c) two scan execution strategies (cheap periodic poll vs event-driven coalesced sweep) sharing one evaluator, directly relevant to scanning ~8000 US equities cheaply; (d) a non-finite-value guard as a single choke point — a subtle correctness lesson worth baking in from day one rather than discovering in production; (e) audit-separated alert history from live-watch state.

**Adopt — the core design to port for `vinu-screener`:**
- The condition JSON schema wholesale: `{indicator, params, field, offset, operator, compare_mode, value|compare_indicator, compare_params, compare_field, compare_offset}` leaf + `{children, logic, negate}` group. Maps directly for Vina: `indicator` = feature name (`pct_change`, `dollar_volume`, `rsi`, `sma`), `offset` for "N bars ago," `compare_mode: indicator` for feature-vs-feature comparisons (e.g. price crosses above its own SMA20) without needing a second rule type.
- Two-tier execution, with **poll mode as the right default for an 8000-symbol screener** — batch-fetch candles for the whole universe on a fixed interval, floored at a rate-limit-safe minimum (FinceptTerminal floors at 30s). The realtime-quote-subscription mode doesn't scale to 8000 symbols anyway and shouldn't be the first thing built. Port the edge+cooldown gating from `ScanMonitor::on_candles` largely as-is.
- The auto-computed required-lookback calculation — before running any rule against the universe, statically walk the rule's condition tree to compute the minimum bars of history needed, and skip/mark-warming any symbol with less history rather than silently evaluating on truncated windows.
- The non-finite guard as a single choke point — with 8000 symbols, some will have zero volume, zero price, delisted gaps, etc., producing inf/-inf in ratio-based features; guard every operand before any comparison. Port the reasoning verbatim, not just the mechanism.
- Keep the scanner **fully decoupled from the order/research/news pipeline**, matching the requirement that it surfaces a candidate list without touching the downstream pipeline until the user explicitly selects a symbol — FinceptTerminal's own architecture (explicitly commented "alert-only, no position/order machinery here") independently validates this is the right boundary.
- The `actions` JSON bag pattern on the rule/watch object — lets each screener rule independently choose Telegram/Discord/none without a new schema per notification channel.
- The fired-watch retention split — match events written to a permanent audit table even when the "live" rule state is reset/removed, giving `vinu-screener` a clean audit trail of "why did this symbol get surfaced," separate from the rule's current active/inactive status.
- The one-shot vs persistent mode distinction as a per-rule config choice — some screener rules should fire once and deactivate (avoid re-surfacing the same candidate daily), others should keep scanning and re-fire outside a cooldown window — two real, distinct product behaviors Vina will need to choose between per rule.

## Where Vinu Excels

- **A statistically rigorous promotion gate before anything trades.** FinceptTerminal's `algo_engine` scanner is alert-only by design (explicitly, deliberately, "no position/order machinery here"), and its separate `DeploymentRunner` gates *orders* on human approval — but neither layer has anything like `vinu-research`'s deflated-Sharpe/holdout/stress-test statistical validation of a strategy's edge before it's ever allowed to generate a signal in the first place.
- **LLM-assisted research generating the candidate strategies themselves.** FinceptTerminal's 37 "AI Agents" (Buffett, Graham, Lynch, etc.) produce discretionary commentary/opinions; Vina's research pipeline produces structured, artifact-based strategies that pass through a formal quantitative gate — a different and more rigorous use of LLM output.
- **A Python-native execution stack**, avoiding the C++/Qt desktop-app architecture's inherent friction for a small team wanting to move fast on the research/ML side — Vina's per-service Python architecture keeps research, data ingestion, and execution in one consistent language and tooling ecosystem.
- **Purpose-built as a headless trading service**, not a desktop terminal application. FinceptTerminal is fundamentally a GUI product with trading capability bolted on; Vina is fundamentally a trading system, so its execution/risk paths don't have to route through or accommodate a UI layer at all.
