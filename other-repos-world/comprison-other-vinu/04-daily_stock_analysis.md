# daily_stock_analysis (DSA)

https://github.com/ZhuLinsen/daily_stock_analysis · 25K stars · First released 2026-01-10 · Last updated 2026-09-06

**Highest-value repo of the 13 for `vinu-screener`** — this is the only repo audited that already ships a production rule-based full-market scanner end-to-end.

## Advanced Features

- **Rule-based full-market screening pipeline** with a documented multi-stage flow: strategy load → snapshot+normalize → hard filter → factor score+risk adjust → candidate context → LLM re-rank (degradable) → risk/portfolio constraints + near-score rotation → top-candidate enrichment → persist. (`docs/screening-engine.md:60-73`; implemented across `src/services/screening/{filter.py,scorer.py,risk.py,ranker.py,pipeline.py}` and `src/services/screening_service.py`, 3,893 lines.) Explicitly ported (with attribution) from AlphaSift.
- **`HardFilterConfig`** — ~35 declarative numeric filter knobs (price/amount/market-cap/PE/PB bands, volume-ratio, turnover, MACD/RSI status whitelists, breakout/pullback/consolidation/volatility/ATR bands, `signal_score_min`). `src/services/screening/models.py:12-50`. This is essentially the rule-DSL a `vinu-screener` needs, already fielded and iterated on.
- **Source-priority snapshot fetch with a generic timeout guard** — `call_with_timeout`/`SourceCallTimeout` (`src/services/screening/source_guard.py:39-72`) runs any 3rd-party blocking call on a daemon thread with a hard deadline, since Python can't force-kill a stuck call. Used to bound ~8000-symbol-scale snapshot/hotspot fetches with configurable per-stage timeouts.
- **Last-good-cache + source-health fallback** — full-market snapshot caches with TTL; on total real-source failure, falls back to a max-staleness-bounded last-good cache and flags results `stale`/`fallback`. A `/screening/source-history` endpoint reports historical source hit/error/degradation counts.
- **Independent risk overlay on screened picks** (`apply_risk_overlay`) — bounded, capped penalty scoring (chase/breakdown momentum, abnormal volume ratio, high turnover, invalid PE, high PB, weak technical signal, MACD-bearish/RSI-overbought, low LLM confidence, LLM-declared risks, deep-analysis risk flags, and **daily-history data-quality risk** — stale cache, fetch-failed, fallback errors treated as risk points), with an optional hard veto (`veto_high_risk`) that excludes rather than just penalizes. `src/services/screening/risk.py:50-83,141-199`.
- **Portfolio/sector concentration overlay** — penalizes repeated sector/theme buckets among top picks (configurable bucket map + alias canonicalization, e.g. brokers/banks/insurance → "金融") so the shortlist isn't one crowded trade. `risk.py:86-138,250-268`.
- **Deterministic "near-score rotation" for result diversity** — a per-session anonymous seed perturbs only the *bottom half of near-score candidates* (must be within 1.5 points of the original cutoff), while hard filters, risk vetoes, and top-half/high-score picks stay protected. Explicitly described as not random re-scoring. `docs/screening-engine.md:86-90`.
- **LLM re-rank that degrades gracefully** — if the primary model returns empty/non-JSON/insufficient coverage, falls back through configured backup models before falling back to pure factor ranking, with attempted-model and failure-reason surfaced in the result (`ScreenResult.llm_attempted_models`, `llm_failure_reason`, `ranking_mode`).
- **Live-editable configuration registry with rich per-field metadata** — `_FIELD_DEFINITIONS` gives every env/config key a title, description, category, `data_type`, `ui_control`, `is_sensitive`, `is_required`, `default_value`, `validation` (min/max/enum/pattern/multi-value), `examples`, doc links, and `warning_codes` — a single source of truth driving the settings UI, validation, and docs simultaneously. `src/core/config_registry.py:20-83`, 5,183 lines total covering hundreds of knobs.
- **Atomic, optimistic-concurrency `.env` config manager** — `ConfigManager.apply_updates` reads current+raw values, skips masked-sensitive-value writes, computes only the diff, does an atomic temp-file + `os.replace` write (with in-place fallback for `EBUSY`/`EXDEV`), and exposes a deterministic `get_config_version()` (mtime+sha256) for optimistic-lock PATCH semantics. `src/core/config_manager.py:112-289`.
- **Notification noise control** — process-local dedup (TTL), cooldown, quiet-hours (`HH:MM-HH:MM`), min-severity gating, and in-flight reservation (prevents duplicate concurrent sends racing past dedup/cooldown checks). `src/notification_noise.py:27-71`.
- **Per-notification-type channel routing** — separate channel lists for `report`/`alert`/`system_error` routes across 14 channels (wechat, dingtalk, feishu, telegram, email, pushover, ntfy, gotify, pushplus, serverchan3, custom, discord, slack, astrbot). `src/notification_routing.py:13-47`.
- **Structured `ResearchArtifact` schema** — every analysis report can emit a machine-readable `thesis` (direction/confidence/score/action/reasons/risks), `evidence[]` (each tagged with `freshness: fresh|stale|unknown` and `quality_level: good|usable|limited|poor|unknown`), and a **mandatory** `invalidation_conditions` list (≥1, auto-derived from stop-loss/take-profit/data-quality/missing-news, else a fallback "manual reassessment" condition). `docs/research-artifact.md:13-63`.
- **Multi-agent disagreement + risk-override reconciliation** — separate technical/risk/portfolio/intel agents each emit typed opinions; `build_agent_disagreement_summary` buckets them bullish/bearish/neutral, and a `RiskOverride` state machine (`RiskTrigger.NONE|RISK_VETO|RISK_DOWNGRADE`, valid downgrade transitions buy→hold→sell only, exhaustive `RiskApplicationReason` enum) can veto or forcibly downgrade the decision-agent's output. `src/agent/disagreement.py:21-79`, `src/agent/risk_override.py:1-60`.
- **Text-based, keyword-driven forward backtest engine** — `BacktestEngine.evaluate_single` parses an LLM's free-text operation advice (buy/sell/hold/wait keyword sets with negation detection) into a direction/position, walks forward daily bars, detects first-hit of stop-loss vs take-profit with documented same-bar ambiguity handling. `src/core/backtest_engine.py:53-91,158-273`.
- **Mature rule-based alerting system with a dry-run test endpoint** — `AlertRuleTestResponse` gives per-target dry-run results (triggered/not_triggered/evaluation_error, degraded/skipped counts) before a rule goes live; delivery is itself audited per-channel with `error_code`/`retryable`/`latency_ms`. `api/v1/schemas/alerts.py:20-147`.
- **Two cleanly separated strategy layers** — `src/services/screening/strategies/*.yaml` (what to screen) vs top-level `strategies/*.yaml` (how to analyze one already-selected stock), with explicit doc language guarding against the two being confused despite occasional same-named files. `docs/screening-engine.md:108-117`.

## Why It's Trusted / Mature

DSA is a genuinely multi-market, multi-broker, multi-LLM-provider system (CN/HK/US via Sina/Tencent/AkShare/Tushare/Futu/Longbridge/YFinance/Finnhub/AlphaVantage) with graceful per-source degradation built in at every layer — not an afterthought. It's a full-stack product (FastAPI backend, React web, Electron desktop, four chat-bot integrations), and the screening engine specifically has roughly two years of real iteration behind it, evidenced by details that only emerge from production use: the "near-score rotation" diversity mechanism, the distinction between one-shot and persistent notification channels, and the explicit doc language warning maintainers not to confuse the two differently-scoped `strategies/*.yaml` layers. The atomic optimistic-concurrency config manager and the field-metadata-driven settings registry both reflect a team that has been burned by config races and undocumented settings before and engineered around it deliberately.

## vs Vinu — Gap & Adoptable Logic

**Gap:** This is the single biggest gap of anything audited. Vina is *designing* `vinu-screener` from scratch; DSA already ships a working, documented, production one — with dry-run testing, staleness/degradation reporting, and diversity/anti-concentration logic that Vina hasn't even scoped yet. Beyond the screener itself: DSA's alert rules have dry-run/test-before-enable plus a per-delivery-attempt audit trail, which Vina's Telegram/Discord notify paths currently lack entirely. DSA's config-field metadata registry is a more complete version of the same idea behind Vina's new runtime-settings admin API, which today is a bare whitelisted-numeric-knobs GET/PATCH. Vina's `vinu-live` has a contingency/invalidation rule engine, but DSA's `ResearchArtifact.invalidation_conditions` is a smaller, cleanly-typed schema (with evidence freshness/quality tagging) worth comparing against for schema completeness. And Vina has no notification noise-control layer (dedup/cooldown/quiet-hours/in-flight reservation) at all — DSA's is a small, portable module.

**Adopt (highest priority — this maps directly onto active Vina work):**
- Port the screening **pipeline shape** wholesale for `vinu-screener`: cached/health-tracked snapshot → declarative hard filter → factor score → independent risk overlay (additive, capped, optional veto) → portfolio/sector concentration overlay → optional near-score rotation for UX diversity → top-N enrichment only.
- Port the `HardFilterConfig` dataclass pattern directly as the shape of `vinu-screener`'s user-defined rule conditions — it's already a clean, fielded "cheap price/volume feature range filter" DSL for ~8000 equities.
- Port `source_guard.call_with_timeout` as-is — a generic daemon-thread timeout wrapper is exactly what's needed to bound an 8000-symbol scan against flaky/slow upstream calls without risking the whole scan hanging.
- Port the risk-overlay-as-penalty-not-filter pattern as a cheap complement to `vinu-agent`'s TradingMandate risk limits, applied at the screener stage rather than only at order-execution stage.
- Port the dry-run/test-rule-before-enable UX (from `AlertRuleTestResponse`) for `vinu-screener`'s user-defined rules — validate a rule against current market data and show per-target trigger/degraded/skipped counts before it runs unattended.
- Note: DSA's screener stays isolated from downstream LLM/order pipelines exactly the way the planned `vinu-screener` design intends — independent validation that the intended architecture is right.

**Adopt (extends the just-shipped runtime-settings admin API):**
- The field-metadata-as-single-source-of-truth pattern (title/description/category/data_type/ui_control/sensitivity/validation/default/examples/warning_codes per knob) so the admin API, any future UI, and docs stay in sync automatically instead of drifting.
- The atomic write + optimistic version token pattern (`get_config_version()` = hash+mtime, diff-only PATCH, masked-sensitive-value writes skipped rather than overwritten) — directly applicable to hardening Vina's GET/PATCH runtime-settings endpoint against races and accidental secret-clobbering.

**Adopt (risk guards / notifications):**
- The portfolio/sector concentration bucket-penalty pattern for `vinu-portfolio`'s correlation/concentration caps — a softer, graduated complement to a hard concentration cap.
- The exhaustive risk-override reason-code enum + valid-transition set as a model for making `vinu-agent`'s TradingMandate kill-switch/reduce-only decisions individually auditable.
- Port `notification_noise.py`'s dedup + cooldown + quiet-hours + severity + in-flight reservation into `vinu-agent`'s/`vinu-live`'s Telegram/Discord notify paths — stops duplicate/noisy alerts, especially around kill-switch and halt-policy events which can otherwise fire repeatedly.
- Port the per-notification-type channel routing table so Vina can route kill-switch/system-error alerts to a different, more urgent channel than routine daily summaries.
- Port the per-delivery-attempt audit trail so Vina can confirm "did the Telegram alert actually land" instead of only logging send-attempted.

## Where Vinu Excels

- **Vina actually trades.** This is the single biggest asymmetry: DSA is an analysis/dashboard/notification product — it screens, ranks, and reports, but nowhere in its architecture does it place a live broker order. There is no TradingMandate, no kill switch, no reduce_only exemption, no book↔broker reconciliation, because there's no book or broker to reconcile. Vina's entire `vinu-agent`/`vinu-live` execution stack is functionality DSA has no need for and therefore no equivalent of — the comparison here is genuinely "mature scanner" vs. "mature scanner *plus* a full live-trading risk-guard stack neither repo needed to build for the other's use case."
- **A statistically rigorous promotion gate**, not a scored/ranked shortlist. DSA's `HardFilterConfig` → factor score → risk overlay pipeline produces a ranked list of *candidates for a human to read*; it doesn't claim any of them are validated against overfitting the way `vinu-research`'s deflated-Sharpe + holdout + stress-test gate does before something is allowed to become `ACTIVE` and actually tradeable.
- **Single-broker depth over multi-source breadth.** DSA's strength (many data sources, many markets, many LLM providers, graceful degradation everywhere) is also a maintenance surface Vina deliberately avoids — Vina's Alpaca-only, US-equities-only scope means less to keep working, at the cost of the breadth DSA has.
