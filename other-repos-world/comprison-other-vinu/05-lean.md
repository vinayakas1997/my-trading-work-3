# Lean (QuantConnect)

https://github.com/QuantConnect/Lean · 21.5K stars · First released 2014-11-28 · Last updated 2026-09-09

## Advanced Features

- **Algorithm Framework's 5-stage pipeline** (`Algorithm.Framework/{Selection,Alphas,Portfolio,Execution,Risk}`) — Universe Selection → Alpha → Portfolio Construction → **Risk Management** (post-construction target adjustment) → Execution, each stage a swappable interface (`IRiskManagementModel`, `IPortfolioConstructionModel`, etc.). Notably, Risk Management runs *after* portfolio construction and can veto/shrink `IPortfolioTarget`s before they reach execution — a distinct architectural position from most systems that only check risk pre-order.
- **Two-stage Coarse→Fine universe selection** (`FundamentalUniverseSelectionModel.cs`, `QC500UniverseSelectionModel.cs:1-60`) — a coarse filter over the entire ~8000-symbol US equity universe (price/volume/has-fundamental-data cheap filters) narrows to ~1000, then a fine filter applies fundamental data to narrow to 500. Exactly the two-tier cheap-filter → expensive-filter pattern relevant to a full-market scanner. `QC500UniverseSelectionModel` rebalances monthly and dollar-volume-ranks candidates.
- **`MaximumSectorExposureRiskManagementModel`** (`Algorithm.Framework/Risk/MaximumSectorExposureRiskManagementModel.cs:29-70`) — caps portfolio exposure per sector as a % of `TotalPortfolioValue`, scaling down `PortfolioTarget`s that would breach it. A concentration cap implemented as a target-rescaling operation, not just a reject/allow gate.
- **`TrailingStopRiskManagementModel`** (`Algorithm.Framework/Risk/TrailingStopRiskManagementModel.cs:26-70`) — tracks a `HoldingsState` (highest unrealized value) per symbol and flattens if drawdown from peak exceeds `_maximumDrawdownPercent`. A per-position trailing-stop implemented as a portfolio-level risk model, decoupled from the alpha/strategy code.
- **Pluggable, security-type-specific `FillModel`/`SlippageModel`/`FeeModel`** (`Common/Orders/Fills/EquityFillModel.cs`, `FutureFillModel.cs`, `FutureOptionFillModel.cs`, `ImmediateFillModel.cs`) — each order type (`MarketFill`, `StopMarketFill`, `StopLimitFill`, `LimitFill`, `MarketOnOpenFill`, `MarketOnCloseFill`) has its own fill-rate/slippage logic, and models are attached per-`Security`, so different instruments can use different realism assumptions in the same backtest.
- **`VolumeWeightedAveragePriceExecutionModel`/`StandardDeviationExecutionModel`/`SpreadExecutionModel`** (`Algorithm.Framework/Execution/`) — execution-layer algos that slice orders based on historical VWAP volume profile, standard-deviation bands, or bid/ask spread thresholds before submitting, i.e. execution-cost-aware order slicing distinct from the fill model itself.

## Why It's Trusted / Mature

Lean's trust case is extremely mature "Reality Modeling" — QuantConnect's own term for the idea that every order type has its own historically-validated fill/slippage/fee model rather than one generic assumption applied everywhere. Calendar/holiday/market-hours handling is exhaustive (`Data/market-hours/`), covering the kind of edge cases (early closes, exchange-specific holidays) that quietly corrupt backtests elsewhere. The framework's staged pipeline lets a risk model veto or shrink *already-constructed* portfolio targets, which catches interactions between the portfolio-construction and execution stages that a purely pre-trade, single-order check would miss entirely — this is a genuinely different risk posture from most retail-focused frameworks, closer to how an institutional desk would structure the checks.

## vs Vinu — Gap & Adoptable Logic

**Gap:** Vina's TradingMandate risk checks are pre-order (agent decides → mandate checks → submits), but Lean demonstrates a complementary post-construction risk stage that operates on the full target portfolio, catching things like sector concentration that only exist at the *portfolio* level, not the single-order level. Vina's correlation/concentration caps partially cover this idea, but aren't structured as a distinct target-rescaling stage the way Lean's `IRiskManagementModel` is — Vina checks orders as they come, not a full proposed target set at once. Vina also lacks Lean's per-instrument-type pluggable fill model architecture (vinu-simulator has Almgren-Chriss, but it's not clear it's per-security-type swappable), and Lean's two-stage coarse→fine universe selection is a directly reusable design for `vinu-screener` that Vina doesn't yet have implemented.

**Adopt:**
- **Coarse→Fine two-stage selection** — the single most directly applicable pattern here for `vinu-screener`: run cheap price/volume filters over all ~8000 symbols first (coarse), then apply more expensive rule evaluation only to the surviving subset (fine). A concrete performance/architecture template, not just "filter in two passes" as a vague idea.
- **Risk-management-as-target-rescaling stage** (pattern: compute `maximumExposureValue = TotalPortfolioValue * cap`, then shrink/zero out `PortfolioTarget`s that would breach it) — port this shape into `vinu-portfolio`/`vinu-agent` for correlation/concentration caps: operate on the *full proposed target set* post-construction rather than checking one order at a time, catching multi-order breaches the current per-order TradingMandate check might miss.
- **`TrailingStopRiskManagementModel`'s peak-tracking `HoldingsState`** — a simple, concrete per-position trailing-drawdown-from-peak flatten mechanism worth comparing against `vinu-live`'s OOD emergency-flatten detector; this is a narrower, cheaper, complementary trigger (per-symbol, not whole-book).
- **Per-security-type fill model dispatch** — even though Vina is equities-only today, the pattern of attaching a fill/slippage model per instrument (rather than one global model) is worth adopting in `vinu-simulator` now, since illiquid small-caps vs. liquid large-caps plausibly warrant different fill assumptions even within "US equities only."

## Where Vinu Excels

- **LLM-driven strategy research with a human-reviewable artifact**, not just an `IAlphaModel` interface a programmer implements. Lean's Algorithm Framework requires writing C#/Python alpha-generation code per strategy; Vina's research pipeline produces artifacts an LLM generated and a human/statistical gate reviewed before anything trades — a fundamentally different (and for a small team, far more accessible) way of generating strategies.
- **Live-editable operational config without a redeploy.** Lean's risk models and universe-selection parameters are set in algorithm code and require a redeploy to change; Vina's runtime-settings admin API lets an operator adjust thresholds on a running process.
- **Simplicity proportional to actual need.** Lean's 5-stage framework and per-security-type fill models are built for genuinely multi-asset (equities/options/futures/crypto/forex), multi-broker institutional use; Vina's flatter, Alpaca-only architecture is easier for a small team to reason about end-to-end, at the acceptable cost of not needing Lean's full generality.
