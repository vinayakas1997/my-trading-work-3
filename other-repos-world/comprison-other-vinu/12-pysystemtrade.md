# pysystemtrade

https://github.com/robcarver17/pysystemtrade · ~2K stars · First released 2015-11-27 · Last updated 2026-07-18

Rob Carver's futures systematic trading framework — his own live capital system, open-sourced with the full production control-plane included, not just backtest code.

## Advanced Features

- **Multi-factor "risk overlay" that scales the whole portfolio down, not per-instrument** — `systems/risk_overlay.py:get_risk_multiplier()` computes four independent risk multipliers (normal risk vs vol target, "shocked" stdev risk, sum-of-abs-risk under correlation-shock assumption, and leverage) and takes the **min** (most conservative) across all four, applied as a single scalar 0..1 multiplier to every position simultaneously. `multiplier_given_series_and_limit()` (same file) is the reusable "how far over the limit are we, scale down proportionally" primitive.
- **Full covariance-based portfolio risk calculation over time**, not just static correlation — `sysquant/portfolio_risk.py:calc_portfolio_risk_series()` walks a time index, builds a covariance matrix per date from a correlation-matrix history combined with a stdev estimate series, and computes portfolio stdev from it. Falls back to a "boring" (zero off-diagonal) correlation matrix if none is available yet, rather than failing outright.
- **Persistent, per-instrument AND per-instrument-strategy trade-count/quantity limits stored in a DB, with automatic staleness cleanup** — `sysproduction/data/controls.py` class `dataTradeLimits`: `what_trade_qty_possible_for_instrument_strategy`, `what_trade_qty_possible_for_instrument_code`, `add_trade`/`remove_trade` (decrement on cancel), `get_all_limits()` prunes limits for instruments no longer traded.
- **Formal Override system with typed reasons and precedence order** — `sysproduction/data/controls.py` class `diagOverrides`: overrides can be set at instrument level, instrument+strategy level, or come from static config, with named override types (`bad_instrument_override`, `duplicate_instrument_override`, `ignored_instrument_override`, `untradeable_instrument_override`) and `get_cumulative_override_for_instrument_strategy` that resolves the *most restrictive* applicable override across all sources.
- **Locks per instrument** (`dataLocks`) — a separate mechanism from overrides, for temporarily blocking trading on an instrument (e.g. during a broken data feed), independently settable/clearable.
- **Layered execution algo hierarchy for order-slicing/timing**, not just "submit and wait" — `sysexecution/algos/algo_market.py`, `algo_adaptive.py`, `algo_limit_orders.py`, `algo_original_best.py`, each defining a broker order type and an order-timeout policy tailored to that execution style.
- **Order stack architecture with three levels** (`sysexecution/order_stacks/{instrument,contract,broker}_order_stack.py`) — a strategy-level "instrument order" spawns "contract orders" (roll-adjusted) which spawn "broker orders"; `sysexecution/stack_handler/` has dedicated modules for `fills.py`, `cancel_and_modify.py`, `balance_trades.py`, `roll_orders.py`, `spawn_children_from_instrument_orders.py` — a genuine state machine for reconciling three layers of order objects against what the broker actually reports.
- **Temporary reduce-only overrides** — `updateOverrides.add_temporary_reduce_only_for_instrument()` is conceptually identical to Vina's reduce_only exemption pattern, but implemented as a DB-persisted temporary override rather than an in-memory flag.

## Why It's Trusted / Mature

People trust pysystemtrade because it is Carver's own live capital system, open-sourced with its entire production control-plane exposed — not just backtest code. DB-backed trade limits, override/lock layers, a three-tier order stack with explicit reconciliation handlers, and a risk overlay that is provably conservative (the min of four independent risk views, so no single risk model's blind spot can let leverage run away) all point at a system built by someone who has had to explain exactly what happened after something went wrong, and engineered the audit trail in from the start. It's deterministic and inspectable — every risk/trade decision traces to a stored, queryable object (Mongo-backed) — and there's an interactive CLI for a human to inspect/override live state, which matters enormously for auditability under real trading conditions.

## vs Vinu — Gap & Adoptable Logic

**Gap:** Vina's TradingMandate has per-symbol and portfolio-wide daily order caps described as agent-level checks, but pysystemtrade's trade-limit system is **persisted, queryable, and independently resettable per instrument/instrument-strategy with automatic stale-limit pruning** — a durable, inspectable control layer, not just an in-process guard that resets on restart with no history. Vina also has nothing equivalent to pysystemtrade's **three-tier order-stack reconciliation with dedicated cancel/modify/balance-trade/roll handlers** — `vinu-live`'s book↔broker reconciliation is closer to this idea, but pysystemtrade's stack_handler decomposition (one file per failure mode) is a cleaner decomposition pattern Vina currently lacks. Also missing: a **formal Override taxonomy** (bad/duplicate/ignored/untradeable) with explicit precedence resolution — Vina's kill switch is binary/global, whereas this gives instrument-granular, reasoned, semi-permanent states.

**Adopt:**
- The "min of independent risk multipliers, applied as one portfolio-wide scalar" pattern — port into `vinu-agent`'s TradingMandate: compute separate multipliers for (a) correlation/concentration cap breach, (b) capital utilization breach, (c) a "shocked vol" what-if, then take `min()` and scale intended order size by that multiplier instead of a hard reject/allow. A smoother risk response than a binary gate.
- The persisted, per-instrument trade-limit object — as the storage-backed implementation for Vina's "max daily orders per-symbol and portfolio-wide," giving resettability, auditability, and staleness cleanup for free, and a natural fit with the new runtime-settings admin API (limits become PATCH-able rows, not just numeric knobs).
- The Override taxonomy pattern — for `vinu-live`'s halt/cooldown-after-losses feature: instead of one global halt flag, support per-symbol "untradeable"/"reduce_only"/"ignored" overrides with reasons and precedence resolution, generalizing the existing reduce_only exemption pattern rather than treating it as a one-off special case.
- Covariance-over-time computation with its graceful cold-start fallback — useful for `vinu-portfolio`'s correlation matrix / rebalancing, specifically the "fall back to a zero-correlation matrix when no correlation history exists yet" pattern, for cold-starting `vinu-live`'s runtime correlation monitor for newly-added symbols.

## Where Vinu Excels

- **LLM-assisted research generating strategies**, versus pysystemtrade's hand-coded, futures-specific trading rules written by Carver himself. Vina's research pipeline is designed to produce and vet new candidate strategies systematically; pysystemtrade's rules are a fixed, manually-authored system tuned to one person's futures trading style.
- **Live-editable config via a modern HTTP admin API.** pysystemtrade's overrides/locks are managed through an interactive CLI against a Mongo backend — powerful, but built for one operator's terminal session. Vina's runtime-settings admin API is a standard authenticated REST surface any authorized tool or dashboard can call.
- **Built for the asset class Vina actually trades.** pysystemtrade is a futures system — position sizing, rolls, margin, and its whole risk-overlay math assume futures contracts. Vina's guards (market-hours checks, no-margin equities assumptions, `reduce_only` order semantics) are built specifically for US cash equities, where several of pysystemtrade's core mechanisms (contract rolls, leverage-based risk multipliers) don't apply at all.
