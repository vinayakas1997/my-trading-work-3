# NautilusTrader

https://github.com/nautechsystems/nautilus_trader · 28.6K stars · First released 2018-06-25 · Last updated 2026-09-10

## Advanced Features

- **Rust-native `RiskEngine`** (`crates/risk/src/engine/mod.rs`, config in `crates/risk/src/engine/config.rs`) — pre-trade checks (`check_order`, `check_order_price`, `check_order_quantity`, `check_orders_risk_for_account`, `check_cash_sell_balance`) enforcing a per-instrument `max_notional_per_order` that is **live-mutable at runtime** via `set_max_notional_per_order()` (no restart needed), plus a `TradingState` enum (`Active`/`Halted`/`Reducing`) toggled through `set_trading_state()` that publishes a `TradingStateChanged` event over the internal message bus — a live kill-switch with a built-in audit trail.
- **Token-bucket `RateLimit`/`Throttler`** (`crates/common/src/throttler.rs`) — used for `max_order_submit`/`max_order_modify` rate limiting (100/sec default). A generic, reusable async throttling primitive, not a bespoke counter tied to one specific check.
- **Trait-based, swappable `FillModel`** (`crates/execution/src/models/fill.rs:46-90`) — `is_limit_filled()`, `is_slipped()`, `fill_limit_inside_spread()`, and `get_orderbook_for_fill_simulation()` are all pluggable, supporting probabilistic partial fills, one-tick slippage injection, and synthetic order-book liquidity generation for backtests — decoupled from the matching engine itself.
- **Rust execution algorithms run inside the actor system** — `TwapAlgorithm` (`crates/trading/src/algorithm/twap.rs`) spawns child orders on a timer (`horizon_secs`/`interval_secs`) using the same `DataActor`/event infrastructure as live trading, so backtest and live execution-algo code paths are identical, not merely "structurally similar."
- **Unified core in Rust with Python bindings (PyO3)** — the entire event bus, clock, risk/portfolio/execution engines are implemented once in Rust (`crates/`) and exposed to Python (`python/nautilus_trader/`), guaranteeing backtest/live logic parity at the binary level — literally the same compiled engine, not just "the same Python code path" the way most Python-only frameworks achieve parity.

## Why It's Trusted / Mature

Nautilus's pitch is nanosecond-precision, deterministic, identical-code-path backtest/live parity backed by a statically-typed Rust core, combined with a formal pre-trade risk engine that operates independently of strategy code and cannot be bypassed by a buggy strategy. That combination — compiled-core determinism plus a strategy-independent, mandatory risk gate plus runtime-mutable risk knobs with an emitted change event — is the trust anchor for anyone running real capital against it. The fact that risk-limit changes are broadcast as typed events rather than silently applied also means every other part of the system (logging, monitoring, other strategies) can react to a risk-state change in real time, which is a meaningfully different guarantee than a config value simply being updated somewhere.

## vs Vinu — Gap & Adoptable Logic

**Gap:** Vina's TradingMandate risk limits live inside `vinu-agent` (co-located with the LLM agent/order execution), whereas Nautilus's risk engine is architecturally a *separate*, mandatory choke-point every order passes through regardless of which strategy/actor emitted it — its limits are runtime-mutable with an emitted audit event, which is exactly the direction Vina's new runtime-settings admin API is heading, but Nautilus already has it wired directly into the risk-check hot path with audit events, not just a generic key-value store behind a PATCH endpoint. Vina also has no order-submission rate limiter (token-bucket burst guard) — TradingMandate's "max daily orders" caps a daily total, but nothing guards against a sub-second burst of submissions.

**Adopt:**
- `set_max_notional_per_order()` + `TradingStateChanged` event pattern — directly applicable to Vina's live-editable runtime-settings API: when a TradingMandate knob changes, emit an audit event on an internal bus (not just persist to DB/memory), so `vinu-live`/`vinu-agent` can react and log a state-change trail, matching Nautilus's `TradingState::Halted` broadcast semantics for kill-switch actions.
- Token-bucket `RateLimit`/`Throttler` — a concrete, generic primitive to add a sub-second order-submission burst limiter to `vinu-agent`'s TradingMandate, complementing (not replacing) its existing max-daily-orders caps.
- `FillModel` trait's four hooks (`is_limit_filled`, `is_slipped`, `fill_limit_inside_spread`, `get_orderbook_for_fill_simulation`) — a clean interface shape to adopt in `vinu-simulator`: separate "does this limit order fill," "does it slip a tick," and "synthetic book for fill simulation" into independently swappable, unit-testable strategies instead of one large simulator function.
- Consider whether `vinu-agent`'s TradingMandate checks should be refactored out of the agent loop into an independent, always-invoked checkpoint (mirroring Nautilus's `RiskEngine.check_order`), so no code path — LLM-driven or otherwise — can submit an order without passing through it.

## Where Vinu Excels

- **LLM-assisted research with a human-gated promotion pipeline.** Nautilus's engine is deliberately mechanical and deterministic — it has no research/strategy-discovery layer at all, let alone one with a deflated-Sharpe/holdout/stress-test gate. Vina's entire `vinu-research` → promotion → `vinu-agent` flow is a category of functionality Nautilus doesn't attempt.
- **Live-editable config without needing to touch Rust or rebuild.** Nautilus's `set_max_notional_per_order()` is a great pattern, but it's still a compiled-core API call an operator can't reach without writing more code; Vina's runtime-settings admin API is already a live HTTP surface any authorized caller can PATCH today.
- **Approachability for a small team.** Nautilus's Rust-core-plus-PyO3-bindings architecture buys determinism at the cost of a much higher bar to extend or debug — every new risk rule or fill-model tweak needs Rust changes and a rebuild. Vina's all-Python, per-service architecture (each with its own venv/tests) is far cheaper to iterate on for a team this size, which matters more in practice than nanosecond-level determinism for a US-equities, not-HFT strategy.
- **`reduce_only` as a pervasive, consistent exemption**, not just a `TradingState::Reducing` mode — Vina's guards check this per-order across the whole risk stack (kill switch, budget cap, portfolio order cap), rather than requiring a global state transition to unlock risk-reducing behavior.
