# StockSharp

https://github.com/StockSharp/StockSharp · 9.4K stars · First released 2014-12-08 · Last updated 2026-09-07

## Advanced Features

- **Composable, serializable risk-rule engine** — `IRiskManager`/`RiskManager` holds an ordered list of `IRiskRule` objects, each independently processing the raw message stream (`ProcessMessage(Message)`) and each rule is `Save`/`Load` round-trippable to settings storage (live-editable, persistable config). `Algo/Risk/RiskManager.cs:1-69`, `Algo/Risk/IRiskRule.cs`. Concrete rule types cover position size, trade frequency in a rolling time window (`RiskTradeFreqRule.cs:82-133`, tracks `_current`/`_endTime` per rule instance — the same shape as Vina's per-symbol/portfolio-wide daily order caps), order/trade price bounds, slippage, commission (order/trade/transaction level), PnL, and error rate.
- **Explicit, orthogonal risk actions** — `RiskActions` enum = `ClosePositions | StopTrading | CancelOrders` (`Algo/Risk/RiskActions.cs`), decoupled from the rule that triggered them — any rule can be wired to any action, rather than each rule type hardcoding what it does when it fires.
- **Full independent matching engine with margin/stop-out simulation** — `MatchingEngine/MarginController.cs` computes required margin from leverage, validates orders against available money, and computes a margin level (`equity / blockedMoney`) with distinct `MarginCallLevel` and `StopOutLevel` thresholds — a realistic broker-side margin/liquidation simulation Vina doesn't have (equities-only, no margin/leverage modeling currently).
- **Client-side execution algorithms implemented from scratch and unit-tested** — `IcebergAlgo` (re-registers a limit order slice-by-slice, explicitly documented as working around venues that "now ban naked icebergs"), `TwapAlgo` (equal-time-sliced order scheduling with clock-driven `UpdateMarketData`), and a `VwapAlgo` — these are `IPositionModifyAlgo` state machines with `GetNextAction`/`OnOrderMatched`/`OnOrderCanceled`/`Cancel` callbacks, independent of any specific broker adapter.
- **Post-hoc slippage measurement from planned vs. actual fill price** — `SlippageManager.ProcessMessage` records the best bid/ask at order-registration time, then on trade fill computes `(fill_price - planned_price) * side_sign * volume` as realized slippage. `Algo/Slippage/SlippageManager.cs:68-126`.
- **Regulatory-grade breadth** — FIX dialects, GPU-accelerated indicators (`Algo.Gpu`), a full localization stack for compliance-heavy markets, and a trailing-stop price calculator — signals this is built for institutional multi-venue use, not just US equities via one broker.

## Why It's Trusted / Mature

StockSharp is trusted because it's a full-stack, exchange-adjacent platform: its own matching engine means backtests and paper trading run against the same order-matching code as "live," a formally composable and persistable risk-rule DSL means risk logic isn't scattered through strategy code, native margin/leverage/stop-out simulation is realistic rather than approximated, and broker-agnostic execution algorithms (iceberg/TWAP/VWAP) are unit tested independently of any specific exchange adapter. This buys determinism and reuse across live/paper/backtest that bolt-on risk checks — checks added after the fact, one per new requirement — don't give you.

## vs Vinu — Gap & Adoptable Logic

**Gap:** Vina's TradingMandate risk limits are described as a fixed set of checks inside `vinu-agent`, not a serializable, independently-persistable, reorderable list of rule *objects* each mapped to an explicit action. Vina also has no execution-algorithm layer (iceberg/TWAP slicing) — orders appear to go out as whole orders, not sliced — and no margin/leverage model (fine given the equities-only-no-margin scope, but worth noting as a hard gap if that scope ever changes). Vina also lacks StockSharp's clean separation between "risk rule detects a condition" and "action executed" — this decoupling is exactly what Vina's new runtime-settings admin API could plug into if risk-rule *parameters* (not just numeric knobs) became live-editable objects.

**Adopt:**
- The rule object + action enum decoupling — directly applicable to `vinu-agent`'s TradingMandate: model each risk limit (max position pct, max order value, max daily orders per-symbol/portfolio, correlation cap, etc.) as an independent `Save`/`Load`-able rule object with an explicit action, rather than inline checks. This also makes the new runtime-settings admin API's job cleaner — PATCH a rule's parameters directly instead of a flat numeric knob.
- The rolling-window trade-frequency counter pattern (`RiskTradeFreqRule.ProcessMessage`) — a minimal, allocation-free rolling-window counter (`_current`, `_endTime` reset on window rollover) that's a good concrete reference implementation for Vina's "max daily orders per-symbol AND portfolio-wide" limits, especially if they ever need sub-daily windows.
- Iceberg/TWAP client-side execution algorithms — concrete, broker-agnostic state machines (`GetNextAction`/`OnOrderMatched`/`OnOrderCanceled`) worth porting into `vinu-live` or `vinu-agent`'s order execution layer for large-order slicing, complementary to (not replacing) the Almgren-Chriss model already in `vinu-simulator`. TWAP's "remaining unfilled folds into next slice" logic is a specific reusable mechanism.
- The realized-slippage-from-planned-price tracker — a lightweight, broker-agnostic mechanism to measure actual execution slippage vs. best-bid/ask-at-order-time, useful for `vinu-live`'s fill/reconciliation monitoring to detect execution quality degradation, independent of the Almgren-Chriss pre-trade cost model.

## Where Vinu Excels

- **LLM-assisted research feeding a statistically-gated promotion pipeline.** StockSharp is a full trading platform but has no research/strategy-discovery layer at all — strategies are hand-authored C#. Vina's entire `vinu-research` → deflated-Sharpe/holdout/stress-test gate → `vinu-agent` flow is a category of capability StockSharp doesn't have.
- **Right-sized complexity for the actual scope.** StockSharp's institutional breadth (FIX dialects, GPU-accelerated indicators, margin/leverage/stop-out simulation, full localization) is overhead Vina's equities-only, single-broker, no-margin scope simply doesn't carry — a smaller surface area is easier for a small team to keep correct.
- **Python-native, matching the rest of the LLM/ML tooling ecosystem.** StockSharp's C# stack, while a legitimate engineering choice, sits outside the Python-first LLM-agent/data-science tooling Vina's research pipeline depends on — Vina doesn't pay an interop cost to connect research output to execution.
