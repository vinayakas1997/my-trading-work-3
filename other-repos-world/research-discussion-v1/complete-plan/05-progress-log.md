## 2026-09-10 — Stage A begins: A1 + A2 (`vinu-portfolio` correlation hardening)

Re-verified before implementing, per the habit Stage 0 established. Confirmed `compute_correlation_matrix()` was exactly `returns_df.corr()` — raw Pearson, no shrinkage, no PSD repair — and traced its real consumer: `OrderGuard._check_portfolio_concentration` fetches this matrix via `GET /portfolio/state` and uses it to reject/allow real buy orders on `max_pairwise_correlation` grounds. Not a cosmetic metric — a noisy or non-PSD value here has direct order-execution consequences.

While tracing, found a second thing worth fixing that wasn't in the plan: `build_portfolio()` had its *own*, separate, inline `returns_df.corr()` call — the exact same computation as `compute_correlation_matrix()`, duplicated rather than shared. Consolidated both onto one path.

Implementation choice worth recording: sklearn is available in this environment but wasn't a declared dependency of `vinu-portfolio`. Considered hand-rolling the Ledoit-Wolf shrinkage formula to avoid adding a dependency, but decided that was the wrong tradeoff — a subtle bug in a hand-rolled shrinkage estimator feeding real risk decisions is worse than one new, well-established, properly-declared dependency (`scikit-learn>=1.3`). Design: try shrinkage first (also PSD by construction when it succeeds), fall back to raw `.corr()` on any failure (fail-open, matching the codebase's established convention for data-quality guards), then apply spectral PSD-repair unconditionally regardless of which path produced the matrix — a cheap no-op when it's already PSD.

Running the existing test suite surfaced the expected consequence: two tests asserted *exact* ±1.0 correlation from tiny (12-15 sample), perfectly-linear-by-construction synthetic series. Shrinkage correctly pulls small-sample extreme correlations toward less extreme, better-regularized estimates — that's the entire point of using it. Confirmed this wasn't a bug by checking what the tests were actually verifying (strong correlation detected, not exact numeric identity) and loosened the assertions accordingly (`< -0.7`, `> 0.8`) rather than reverting the fix or leaving a red test.

12 new tests total (4 in `test_risk_utils.py` for the module directly, plus `test_service.py` additions: a PSD regression guard using pandas' pairwise-NaN `.corr()` behavior as the known way to produce a non-PSD matrix, plus the 2 loosened assertions). Full vinu-portfolio suite: 143 passed, 2 pre-existing unrelated `test_auth.py` failures (same env-var-dependent pattern already confirmed unrelated in every other service this session).

## 2026-09-10 — Group A-1 finished: A3, A4, A5

**A3 (`TargetPercent`-style order-delta resolution)** — turned out ~90% already implemented. `vinu-live/vinu_live/signal_translator.py`'s `SignalTranslator._build_instruction` already did the full pattern: `target_value = target_w * portfolio_value`, `target_qty = target_value / price`, `delta = target_qty - current_qty`, quantized to whole shares, with the "held but no longer in target_weights → full close" case handled (and its own comment noting *that* was a previously-fixed bug). The one real gap: `price = prices.get(symbol, 1.0)` — a symbol missing from the price dict (network error, 404, empty candles from vinu-stock-price) silently gets priced at 1.0, which for a $200 stock emits an order ~200x too large. `_fetch_prices`'s own docstring even describes fixing this exact class of bug ("silently fell back to a price of 1.0, which made every downstream qty/value computation nonsense") at the fetch layer — but `_build_instruction` reintroduced it downstream. Found the same bug in `scheduler.py`'s `_compute_expected_positions`, which matters more: it feeds reconciliation, and reconciliation auto-corrects drift (close stale / reduce / increase), so a fabricated expected qty could trigger a real corrective order. Both now fail closed — skip the symbol, log a warning, retry next cycle. 2 new tests. vinu-live suite 278 passed (2 pre-existing).

**A4 (concentration bucket-penalty)** — the plan framed this as adopting daily_stock_analysis's graduated penalty; the actual finding was a bug. `allocate_risk_parity` applied `min(w, max_per_strategy_weight)` *before* the normalize step, and renormalization then pushed the capped weight straight back over the cap. Concrete: 3 strategies, one dominant → capped at 0.30, others 0.05 each → total 0.40 → renormalize → 0.30/0.40 = 0.75. `_check_composition_gaps` correctly flags `max_w > 0.4` as "single-name risk" — but nothing acts on that flag. New `cap_concentration()` in `risk_utils.py`: iterative clip-and-redistribute-excess applied *after* normalization, so the cap actually holds. Had to add a `1/n` feasibility floor: with only 2 strategies, a 0.30 cap is impossible (2 × 0.30 = 0.60 < 1), and two existing equal-weight-fallback tests broke on the first pass because both weights got clipped to 0.30 summing to 0.60. Equal weight is the least concentrated a book of n names can be, so the effective cap floors there and a below-`1/n` config cap is a no-op. Deliberately did *not* do the sector-bucketing half of DSA's pattern — Vina has no sector-data source in this path, so that's Stage-C-sized, not cheap hardening. 7 new tests, vinu-portfolio suite 150 passed (2 pre-existing).

**A5 (transaction-cost-aware rebalancing objective)** — skipped, with reason. PyPortfolioOpt's `k * sum(|w - w_prev|)` is a soft penalty term for a *convex optimizer's* objective. Vina's rebalance path (`_apply_regime_tilt`) uses inverse-vol risk-parity + regime tilts, no optimizer — nowhere to attach the term. And it already has two *hard* turnover controls that are arguably stronger: a hysteresis dead-band (`VINU_PORTFOLIO_MIN_WEIGHT_CHANGE`, default 2%, sub-threshold changes hold the old weight) and a per-cycle action cap (`VINU_PORTFOLIO_MAX_ACTION`, default 20%, big rotations phase in gradually). Adding the penalty would be redundant and awkward. First `skipped` item in the plan — the plan's status vocabulary explicitly allows for "reviewed, current approach adequate."

**A10 (turbulence index)** — added as a 4th OOD-detector signal in `orchestrator.py:_check_ood`. The detector already computes a returns covariance for signal 1 (crisis correlation) and fetches per-symbol return series for signals 2/3 (vol explosion, gap move). The Mahalanobis distance `(r_today - r_hist_mean)ᵀ Σ⁻¹ (r_today - r_hist_mean)` reuses both — one `np.linalg.pinv` call, no new I/O. It fires on a statistically extreme *joint configuration* of returns even when no single symbol's vol and no single pairwise correlation looks abnormal on its own, which none of the three existing signals quite captures. Threshold is `OOD_TURBULENCE_MULT` (env, default 5) times the open-book size — under multivariate normality E[MD²] = n, so a flat multiple-of-n is a principled "abnormal" line without needing scipy's chi-squared ppf (scipy isn't a vinu-live dependency). **A13 (realized slippage)** — `_confirm_fill` only ever compared quantities. ## 2026-09-11 — Group A-4 (`vinu-research` promotion-gate hardening): A23 done; A22, A24, A25, A26 skipped

Vina's BENCHING→ACTIVE gate is one of the most carefully-built parts of the whole system — deflated Sharpe with the skew/kurtosis higher-moment correction, PBO via combinatorially-symmetric CV with a configurable embargo, a true out-of-sample holdout the refinement loop never sees, historical stress windows, and a correlation-eligibility gate. **A23 (cross-check the deflated-Sharpe math)** — the one real gap, and it was a *coverage* gap, not a correctness one. `deflated_sharpe_ratio`, `probabilistic_sharpe_ratio`, and `mertens_sharpe_se` live in `vinu-simulator/engine/inference.py`, and `walk_forward.py` re-exports the first one as the source of `artifact.deflated_sharpe` — the number `meets_promotion_bar()` compares against 0.95. Grepped the test suites of both vinu-simulator and vinu-research: **zero direct tests** on any of the three. A safety-critical gate with no unit test is exactly where a future "small refactor" quietly moves the bar. Added `test_inference.py` (15 tests): Mertens SE asserted to collapse to the Lo (2002) closed form under normality; PSR asserted equal to Φ(z); and `deflated_sharpe_ratio` recomputed from scratch in the test from the Bailey & López de Prado (2014) expected-maximum-of-n-trials formula (the same closed form VectorBT documents for its `nb_trials` deflation) and asserted equal across five parameter sets spanning normal and fat-tailed, few and many trials. Plus three behavioural checks: `n_trials=1` DSR equals PSR-against-zero (two independently-written implementations agreeing), DSR strictly decreasing in `n_trials`, and the gate actually discriminating — SR 2.5 as best-of-3 clears 0.95, the same SR as best-of-5000 doesn't. No production code changed.

## 2026-09-11 — C18 done: mandate consent expiry

Vibe-Trading's point: a mandate loaded once at startup and trusted forever is a governance gap — the operator's consent to trade under a given set of limits should have a shelf life. Added `TradingMandate.consent_expires_at` (ISO-8601 string; a naive timestamp is read as UTC; empty string = the prior no-expiry behaviour) and `consent_expired(now=None)`. `TradingMandate.load()` parses it from `mandate.yaml` and logs a WARNING if the mandate it just loaded is already stale; `to_dict()` exposes both the raw `consent_expires_at` and a live `consent_expired` bool (so `GET /agent/broker/mandate` and the existing rejection payloads show it).

`OrderGuard.check()` gets one new gate, right after the C4 symbol-override check and before any numeric limit: if `not reduce_only and mandate.consent_expired()` → reject with `ReasonCode.MANDATE_EXPIRED` and a message that says exactly how to fix it (edit `consent_expires_at`, or hit the renew endpoint). `reduce_only` orders are never blocked by expiry — same "de-risking always gets through" posture as the kill switch and the risk-budget halt.

## 2026-09-11 — The screen ranker: "set the ranks"

User's next request, after asking how the scanner actually runs operationally: build the piece I'd flagged as missing in that explanation -- `ScreenPipeline` (Phase B-3) was fully built and tested but had no runner and no way for a user to define what it ranks *on* without writing Python. "The screener where I can set the ranks."

**The core design decision**: don't touch `ScreenPipeline` at all. It was always built around a plain `ScorerFn = Callable[[dict[str, float]], float]` -- the honest gap wasn't the pipeline, it was that nothing *built* one declaratively. `pipeline/scorer.py`'s `FactorSpec` (`name`/`indicator`/`weight`/`params`/`output_field`/`offset`) reuses the exact shape a condition leaf (B1) already has -- a user configuring "what to rank on" and a user configuring "what condition to check" are filling in the same kind of form, just consumed differently (summed with weights vs. compared against a threshold). `weighted_score()` sums `weight * value` over every factor present and finite in a candidate's fields, silently contributing 0 for anything missing or non-finite (same fail-closed posture as B2's `all_finite`, applied to scoring instead of gating -- one bad factor value shouldn't poison the whole score with a NaN).

**`rankers/` subpackage**, deliberately mirroring `rules/` + `scheduler.py`'s already-proven shape rather than inventing a new pattern for the second time this session:
- `config.py`: `RankerConfig` (universe + factors + top_n + hard filter). `RANKER_MIN_INTERVAL_SEC=300s` -- higher than `ScanRule`'s 30s floor, deliberately: ranking a whole universe with several indicator computations per symbol is heavier per cycle than one condition check, so the same floor logic applies but at a number that actually reflects the cost. `ONE_DAY_SEC=86400` as the natural default, directly answering "will it do it once at start of day" from the earlier question -- yes, and now it's the default rather than something to configure by hand.
- `store.py`: `RankerStore(SQLiteBackend)`, same CRUD + enable/disable + interval-floor-on-write shape as `RuleStore`.
- `runner.py`: `RankerRunner` -- fetches the universe via `get_ohlcv_batch()` when the data source supports it (same duck-typed preference `ScanMonitor` uses, so the earlier bulk-endpoint fix pays off here too), computes each `FactorSpec` via B5's `IndicatorFactory.latest()` -- one broadcast call per factor across the *whole* universe, not one call per symbol per factor -- and always carries `price`/`volume`/`dollar_volume` in every candidate's fields regardless of what factors are configured, since `HardFilterConfig`'s own bounds read those names and a ranker with no price-related factor shouldn't lose hard-filtering because of it.
- `snapshot_store.py`: `RankedSnapshotStore` -- persists the latest ranked result per ranker (symbol/factor_score/risk_penalty/concentration_penalty/final_score/risk_flags), so `GET .../latest` is a cheap read, never a re-run. Deliberately a durable row, not an in-process TTL cache like B20's `PairlistCache` -- a ranker's own schedule (as infrequent as once a day) already controls freshness, there's nothing for a cache layer to add.
- `scheduler.py`: `RankerScheduler`, the same `tick()`/`run_forever()`/per-item error isolation shape as `scheduler.Scheduler` (B18), just running `RankerRunner.run()` against every active `RankerConfig` on its own interval instead of `ScanMonitor.run_cycle()` against `ScanRule`s.

**Wiring**: `server/app.py` gained `GET/PUT/DELETE /screener/rankers/{id}` + `/enable` + `/disable` (identical shape to the rule routes), `POST /screener/rankers/{id}/rank` (on-demand -- runs right now, persists the result as the new latest snapshot, but deliberately never touches `RankerScheduler`'s own due-tracking, so an operator manually re-ranking doesn't delay or skip the next scheduled run), and `GET /screener/rankers/{id}/latest` (the cheap read, 404 if nothing has run yet -- an empty ranking and "never ran" are different facts, same "don't conflate them" instinct as B20's pairlist-cache fail-open design). `cli.py`'s `scan` subcommand now starts `RankerScheduler.run_forever()` on a background daemon thread and runs the existing rule `Scheduler.run_forever()` in the foreground, both sharing one `HttpStockDataSource`/`httpx.Client` -- two schedules in one process, since neither the rule loop nor the ranker loop is expensive enough alone to justify a third container next to `screener-api`'s existing two processes.

## 2026-09-11 — Rank-churn detection: the follow-on the user's own design instinct asked for

Same conversation, immediately after the ranker shipped: the user walked through their own reasoning out loud -- multi-cadence rankers (daily/4h/hourly, already free with the ranker's per-config `interval_sec`), then landed on the actually-new idea: "if 1 hour it's screening out, if we have 20 in the list and any one got out, other ticker came, we will get to know today the predicted is not following through, why, and we can stop -- this is also a parameter down the line." Correctly identified, unprompted, that this wasn't built: `RankedSnapshotStore.set_latest()` *overwrites*, it doesn't keep what came before, so there was nothing to diff a new ranking against. Asked "what do you think of this," confirmed with `AskUserQuestion` that churn detection should come first (ahead of per-ranker candle intervals and Telegram dispatch, both flagged as real but separate follow-ons), and built it.

**`diff_rankings()`** -- the one function that actually matters here, kept deliberately pure (no I/O, no store dependency) so its edge cases could be pinned down in isolation before anything used it: `previous_symbols=None` (the ranker's first-ever run) produces zero events, on purpose -- every symbol in a first ranking is technically "new," but that's the ranker starting to exist, not a churn signal; treating it as churn would mean every ranker's first run floods the churn history with N meaningless "entered" events. A symbol whose *rank position* changes without leaving the top-N (AAPL #1→#2, MSFT #2→#1) produces no events either -- churn means crossing the top-N boundary, not reordering within it. Caught while writing the test for exactly this case (`test_rank_position_shifting_without_membership_change_is_not_churn`) before it became an ambiguity in the real implementation.

**`record_ranking()`** -- the part that took the most care, because it's the one place a subtle bug could have silently corrupted the churn history: both the scheduled `RankerScheduler.tick()` and the on-demand `POST /screener/rankers/{id}/rank` route need to produce *consistent* churn, meaning an operator manually re-running a ranker between two scheduled ticks must diff against whatever the scheduler last saw, and the scheduler's next tick must then diff against the manual run, not skip past it. Solved by making both call the exact same function: read the previous snapshot, THEN overwrite it, THEN diff, THEN persist events -- one code path, so "scheduled vs. manual" can never produce two different ideas of what "previous" meant. Verified with a dedicated test (`test_three_consecutive_runs_each_diff_against_the_immediately_prior_one`) chaining three rankings and checking every pairwise diff landed correctly, not just the first-to-second one.

**`RankerChurnStore`** -- same `SQLiteBackend` permanent-audit-table convention as B17's `WatchAuditStore`, deliberately: a churn event, once recorded, should never be reset or rewritten by anything -- "AAPL exited the top-20 on day 3" stays a fact forever, the same way a fired-watch record does, independent of whatever the ranker's *current* state is.
