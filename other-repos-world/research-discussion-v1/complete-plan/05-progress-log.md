## 2026-09-10 — Stage A begins: A1 + A2 (`vinu-portfolio` correlation hardening)

Re-verified before implementing, per the habit Stage 0 established. Confirmed `compute_correlation_matrix()` was exactly `returns_df.corr()` — raw Pearson, no shrinkage, no PSD repair — and traced its real consumer: `OrderGuard._check_portfolio_concentration` fetches this matrix via `GET /portfolio/state` and uses it to reject/allow real buy orders on `max_pairwise_correlation` grounds. Not a cosmetic metric — a noisy or non-PSD value here has direct order-execution consequences.

While tracing, found a second thing worth fixing that wasn't in the plan: `build_portfolio()` had its *own*, separate, inline `returns_df.corr()` call — the exact same computation as `compute_correlation_matrix()`, duplicated rather than shared. Consolidated both onto one path.

Implementation choice worth recording: sklearn is available in this environment but wasn't a declared dependency of `vinu-portfolio`. Considered hand-rolling the Ledoit-Wolf shrinkage formula to avoid adding a dependency, but decided that was the wrong tradeoff — a subtle bug in a hand-rolled shrinkage estimator feeding real risk decisions is worse than one new, well-established, properly-declared dependency (`scikit-learn>=1.3`). Design: try shrinkage first (also PSD by construction when it succeeds), fall back to raw `.corr()` on any failure (fail-open, matching the codebase's established convention for data-quality guards), then apply spectral PSD-repair unconditionally regardless of which path produced the matrix — a cheap no-op when it's already PSD.

Running the existing test suite surfaced the expected consequence: two tests asserted *exact* ±1.0 correlation from tiny (12-15 sample), perfectly-linear-by-construction synthetic series. Shrinkage correctly pulls small-sample extreme correlations toward less extreme, better-regularized estimates — that's the entire point of using it. Confirmed this wasn't a bug by checking what the tests were actually verifying (strong correlation detected, not exact numeric identity) and loosened the assertions accordingly (`< -0.7`, `> 0.8`) rather than reverting the fix or leaving a red test.

12 new tests total (4 in `test_risk_utils.py` for the module directly, plus `test_service.py` additions: a PSD regression guard using pandas' pairwise-NaN `.corr()` behavior as the known way to produce a non-PSD matrix, plus the 2 loosened assertions). Full vinu-portfolio suite: 143 passed, 2 pre-existing unrelated `test_auth.py` failures (same env-var-dependent pattern already confirmed unrelated in every other service this session).

## 2026-09-10 — Group A-1 finished: A3, A4, A5

**A3 (`TargetPercent`-style order-delta resolution)** — turned out ~90% already implemented. `vinu-live/vinu_live/signal_translator.py`'s `SignalTranslator._build_instruction` already did the full pattern: `target_value = target_w * portfolio_value`, `target_qty = target_value / price`, `delta = target_qty - current_qty`, quantized to whole shares, with the "held but no longer in target_weights → full close" case handled (and its own comment noting *that* was a previously-fixed bug). The one real gap: `price = prices.get(symbol, 1.0)` — a symbol missing from the price dict (network error, 404, empty candles from vinu-stock-price) silently gets priced at 1.0, which for a $200 stock emits an order ~200x too large. `_fetch_prices`'s own docstring even describes fixing this exact class of bug ("silently fell back to a price of 1.0, which made every downstream qty/value computation nonsense") at the fetch layer — but `_build_instruction` reintroduced it downstream. Found the same bug in `scheduler.py`'s `_compute_expected_positions`, which matters more: it feeds reconciliation, and reconciliation auto-corrects drift (close stale / reduce / increase), so a fabricated expected qty could trigger a real corrective order. Both now fail closed — skip the symbol, log a warning, retry next cycle. 2 new tests. vinu-live suite 278 passed (2 pre-existing).

**A4 (concentration bucket-penalty)** — the plan framed this as adopting daily_stock_analysis's graduated penalty; the actual finding was a bug. `allocate_risk_parity` applied `min(w, max_per_strategy_weight)` *before* the normalize step, and renormalization then pushed the capped weight straight back over the cap. Concrete: 3 strategies, one dominant → capped at 0.30, others 0.05 each → total 0.40 → renormalize → 0.30/0.40 = 0.75. `_check_composition_gaps` correctly flags `max_w > 0.4` as "single-name risk" — but nothing acts on that flag. New `cap_concentration()` in `risk_utils.py`: iterative clip-and-redistribute-excess applied *after* normalization, so the cap actually holds. Had to add a `1/n` feasibility floor: with only 2 strategies, a 0.30 cap is impossible (2 × 0.30 = 0.60 < 1), and two existing equal-weight-fallback tests broke on the first pass because both weights got clipped to 0.30 summing to 0.60. Equal weight is the least concentrated a book of n names can be, so the effective cap floors there and a below-`1/n` config cap is a no-op. Deliberately did *not* do the sector-bucketing half of DSA's pattern — Vina has no sector-data source in this path, so that's Stage-C-sized, not cheap hardening. 7 new tests, vinu-portfolio suite 150 passed (2 pre-existing).

**A5 (transaction-cost-aware rebalancing objective)** — skipped, with reason. PyPortfolioOpt's `k * sum(|w - w_prev|)` is a soft penalty term for a *convex optimizer's* objective. Vina's rebalance path (`_apply_regime_tilt`) uses inverse-vol risk-parity + regime tilts, no optimizer — nowhere to attach the term. And it already has two *hard* turnover controls that are arguably stronger: a hysteresis dead-band (`VINU_PORTFOLIO_MIN_WEIGHT_CHANGE`, default 2%, sub-threshold changes hold the old weight) and a per-cycle action cap (`VINU_PORTFOLIO_MAX_ACTION`, default 20%, big rotations phase in gradually). Adding the penalty would be redundant and awkward. First `skipped` item in the plan — the plan's status vocabulary explicitly allows for "reviewed, current approach adequate."

**A10 (turbulence index)** — added as a 4th OOD-detector signal in `orchestrator.py:_check_ood`. The detector already computes a returns covariance for signal 1 (crisis correlation) and fetches per-symbol return series for signals 2/3 (vol explosion, gap move). The Mahalanobis distance `(r_today - r_hist_mean)ᵀ Σ⁻¹ (r_today - r_hist_mean)` reuses both — one `np.linalg.pinv` call, no new I/O. It fires on a statistically extreme *joint configuration* of returns even when no single symbol's vol and no single pairwise correlation looks abnormal on its own, which none of the three existing signals quite captures. Threshold is `OOD_TURBULENCE_MULT` (env, default 5) times the open-book size — under multivariate normality E[MD²] = n, so a flat multiple-of-n is a principled "abnormal" line without needing scipy's chi-squared ppf (scipy isn't a vinu-live dependency). Verified against a realistic small-variance covariance in the test — the existing OOD test fixtures use a unit-variance `_cov` helper, which makes MD² tiny, so the new signal is inert there and the 7 existing OOD tests were unaffected (confirmed).

Added `TRAILING_ACTIVATION_PCT` (env, default 0.0 = unchanged): the trailing stop stays inert until the position is up by that fraction; the plan's fixed invalidation/contingency stops still cover the position in the meantime. Small, self-contained, opt-in.

**A9 (mandatory invalidation conditions)** — `_build_invalidation_conditions` already returns ≥2 unconditionally, so a plan with none can't come from the real authoring path today. **A13 (realized slippage)** — `_confirm_fill` only ever compared quantities. Added `_entry_slippage_bps`: after a confirmed entry *from flat*, fetch the broker's post-fill `avg_entry_price` and compare it to the price the order was sized on, log `± bps` (positive = filled worse), attach `slippage_bps` to the entry action. Gated to entries-from-flat because an add's blended avg-entry isn't this fill's price. Monitoring-only, best-effort, never raises. A durable slippage store + trend analysis (StockSharp's fuller `SlippageManager`) was left out as more than cheap hardening.

## 2026-09-11 — Group A-4 (`vinu-research` promotion-gate hardening): A23 done; A22, A24, A25, A26 skipped

This group turned out to be almost all verification. Vina's BENCHING→ACTIVE gate is one of the most carefully-built parts of the whole system — deflated Sharpe with the skew/kurtosis higher-moment correction, PBO via combinatorially-symmetric CV with a configurable embargo, a true out-of-sample holdout the refinement loop never sees, historical stress windows, and a correlation-eligibility gate. Four of the five items were asking for things that are already there in a form that fits Vina's architecture better than the source repo's form.

**A23 (cross-check the deflated-Sharpe math)** — the one real gap, and it was a *coverage* gap, not a correctness one. `deflated_sharpe_ratio`, `probabilistic_sharpe_ratio`, and `mertens_sharpe_se` live in `vinu-simulator/engine/inference.py`, and `walk_forward.py` re-exports the first one as the source of `artifact.deflated_sharpe` — the number `meets_promotion_bar()` compares against 0.95. Grepped the test suites of both vinu-simulator and vinu-research: **zero direct tests** on any of the three. A safety-critical gate with no unit test is exactly where a future "small refactor" quietly moves the bar. Added `test_inference.py` (15 tests): Mertens SE asserted to collapse to the Lo (2002) closed form under normality; PSR asserted equal to Φ(z); and `deflated_sharpe_ratio` recomputed from scratch in the test from the Bailey & López de Prado (2014) expected-maximum-of-n-trials formula (the same closed form VectorBT documents for its `nb_trials` deflation) and asserted equal across five parameter sets spanning normal and fat-tailed, few and many trials. Plus three behavioural checks: `n_trials=1` DSR equals PSR-against-zero (two independently-written implementations agreeing), DSR strictly decreasing in `n_trials`, and the gate actually discriminating — SR 2.5 as best-of-3 clears 0.95, the same SR as best-of-5000 doesn't. No production code changed.

## 2026-09-11 — C18 done: mandate consent expiry

Vibe-Trading's point: a mandate loaded once at startup and trusted forever is a governance gap — the operator's consent to trade under a given set of limits should have a shelf life. Added `TradingMandate.consent_expires_at` (ISO-8601 string; a naive timestamp is read as UTC; empty string = the prior no-expiry behaviour) and `consent_expired(now=None)`. `TradingMandate.load()` parses it from `mandate.yaml` and logs a WARNING if the mandate it just loaded is already stale; `to_dict()` exposes both the raw `consent_expires_at` and a live `consent_expired` bool (so `GET /agent/broker/mandate` and the existing rejection payloads show it).

`OrderGuard.check()` gets one new gate, right after the C4 symbol-override check and before any numeric limit: if `not reduce_only and mandate.consent_expired()` → reject with `ReasonCode.MANDATE_EXPIRED` and a message that says exactly how to fix it (edit `consent_expires_at`, or hit the renew endpoint). `reduce_only` orders are never blocked by expiry — same "de-risking always gets through" posture as the kill switch and the risk-budget halt.

Renewal without a restart: `POST /agent/broker/mandate/renew` takes `{days: N}` (default 30) or `{until: "<ISO>"}`, computes the new expiry, and rewrites **only** the `consent_expires_at` key back into `mandate.yaml` (load → set one key → `safe_dump`), preserving everything else in the file; it audits the change via `AuditLogger`. Because `OrderGuard` builds a fresh `TradingMandate.load()` per order, the next order picks up the renewed expiry with no restart. `GET /agent/broker/mandate` returns the current mandate dict.

**C11 — Hierarchical Risk Parity allocation mode.** C11 was framed as "HRP as a backstop when the correlation matrix is ill-conditioned even after A1/A2". Re-reading `allocate_risk_parity`, that framing doesn't quite fit Vina: the allocator is *inverse-volatility* — it reads only `returns_df.std()`, never inverts (or even touches) the correlation matrix, so it's already immune to an ill-conditioned Σ. HRP's actual value here is different and real: it's *correlation-aware* (clusters strategies that move together and treats a cluster as one risk unit) while still being inversion-free, so it degrades gracefully where mean-variance / full risk-parity would blow up. Implemented `hrp_weights(returns_df)` in `risk_utils.py`: single-linkage clustering on the `sqrt((1-corr)/2)` distance (using the A1/A2-hardened `robust_correlation_matrix`), quasi-diagonalisation by dendrogram leaf order, recursive bisection allocating inverse-cluster-variance. Returns `None` when there's < n+5 rows of history to cluster on — the caller (`allocate_risk_parity`) then falls through to the existing inverse-vol path, and the `cap_concentration` post-step still applies either way. Exposed as `allocation_mode` (config + `VINU_PORTFOLIO_ALLOCATION_MODE`), **default `"inverse_vol"`** so nothing changes unless an operator opts in. 5 `risk_utils` tests (sums to 1, low-var cluster gets more, `None` on short history / single column / `None`, degenerate identical-columns matrix doesn't raise) + 2 service tests (mode switch works, falls back on short history).

**C12 — post-construction cluster rescaling.** Re-read the item against `_check_composition_gaps`: Vina already *detects* "high correlation cluster max 0.85 — book moves as one" but does nothing about it — the gap C12 names is real. No sector data exists in this path (confirmed again, same finding as A4), so the sector half of Lean's pattern isn't implementable; the correlation half is. `rescale_correlated_clusters(weights, corr, corr_threshold, max_cluster_weight)`: union-find groups names whose pairwise `|corr| >= threshold`; any cluster whose combined weight exceeds the cap gets scaled down proportionally, and the freed weight goes to names outside any over-cap cluster (or is simply renormalised back to 1.0 if the whole book is one cluster — there's nowhere uncorrelated to send it). Wired into `build_portfolio` right after `allocate_risk_parity`, gated on `max_correlated_cluster_weight < 1.0` (default 1.0 = off). This is the multi-name analogue of `cap_concentration` (A4) — that one caps a single name, this one caps a correlated *block* of names, which is exactly the blind spot no per-order OrderGuard check or per-name cap sees.

**C13 — data-derived stress windows.** The fixed COVID/rate-hike windows in `stress_test_windows` are the same for every symbol; a symbol's own worst stretch might not overlap either one. `regime_windows.py`'s `derive_regime_windows()` takes a price or cumulative-return series and finds three spans: deepest drawdown (peak index to the argmin of the drawdown series), sharpest run-up (the mirror image), and steepest sustained decline (the `decline_window_days`-bar sub-window with the most negative level-normalised linear slope, brute-forced since the windows are small). All three are pure numpy/pandas, no I/O, fail safely to `[]` on flat or too-short input. Wired into `_run_stress_test` (needed threading `research_from`/`research_to` through from the caller) behind `stress_test_derive_regime_windows` (default off): fetches the symbol's returns over the full researched range via the tools client, reconstructs a price-equivalent cumulative-return path, derives the windows, and appends them to the fixed list before the existing pass/fail loop runs — so a derived window is scored by exactly the same `max_drawdown >= threshold` rule as a fixed one, no new logic needed there.
